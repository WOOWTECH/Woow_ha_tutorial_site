能源儀表板與 ESG 實踐

冷氣、除濕機、電熱水瓶到底誰最吃電？這章教你把家裡或辦公室的用電變成看得懂的圖表：從挑對 sensor、設定能源儀表板、把「瓦數」積分成「度數」，一路做到電費成本追蹤和一份拿得出手的節能報告。讀完你會知道每一度電花在哪裡，也能用數字證明「我們真的有省下來」。

為什麼要學這個：從「感覺很花電」到「我有數字」

每個月電費單來的時候，大家的反應通常是「怎麼又這麼多」，然後就沒有然後了。因為電費單只告訴你一個總數，它不會告訴你這個總數是哪一台機器貢獻的。

能源儀表板（Energy Dashboard）就是在解這件事。它是 Home Assistant 內建的一個特殊儀表板，會把你的用電資料畫成「今天用了幾度」「這個月每天長怎樣」「哪台裝置吃掉最多」，還可以乘上電價變成錢。

幾個很有感的情境：

  • 家裡：你懷疑舊冰箱很吃電，但沒證據。裝一顆有電力監測的智慧插座，兩週後你會看到它每天穩定吃掉多少度，換新機值不值得一目瞭然。
  • 房間：除濕機忘了關，跑一整天。有了每日用電圖你會馬上發現「這天怎麼多了 3 度」。
  • 辦公室茶水間：飲水機 24 小時保溫，看起來只有幾百瓦，但一個月累積起來可能比影印機還多。這種「小功率但全天候」的怪獸，只有累積數據抓得到。
  • ESG 報告：小型辦公室要交節能或永續說明時，「我們裝了智慧插座，把茶水間熱水器改成上班時段才保溫，月用電下降 X 度」這種寫法，比「我們有宣導隨手關燈」有力太多。
觀念：這章不需要你會寫程式，但需要你有耐心。能源數據跟自動化不一樣，自動化按下去馬上有反應，能源數據要「等」——至少累積幾天才看得出趨勢，一個完整週期（例如一個月）才有比較的價值。

銜接點：這章大量用到附錄 B講過的「輔助元件（Helper）」，也會一直提到第 4 章的實體 ID 與命名。裝置本身怎麼加進 HA，請看第 11 章。如果你連 sensor 是什麼都還不確定，先回第 12 章看 sensor 那一段。

先分清楚兩個字：功率（W）與用電量（kWh）

這是整章最重要、也最多人搞混的觀念。一句話記起來：功率像速度，用電量像距離。

名稱單位它在回答什麼比喻
功率（Power）W、kW「現在」這一秒吃多少電時速 60 公里
用電量（Energy）Wh、kWh（度）「一段時間內」總共用掉多少電今天開了 120 公里

台電收你錢是用度數（1 度 = 1 kWh），不是用瓦數。所以：

  • 一台 1000 W 的電暖器開 1 小時 = 1 度。
  • 一台 100 W 的飲水機開 24 小時 = 2.4 度。比電暖器還多。

很多便宜的智慧插座只會回報「現在幾瓦」（功率），不會回報「累積幾度」（用電量）。能源儀表板最想要的是用電量——所有「今天用了幾度」「這個月花多少錢」的圖表都是從度數來的。這就是為什麼你常常會遇到「我明明有電力監測，可是儀表板選不到我的插座」。

觀念：功率 sensor 也不是完全沒用。官方文件寫「如果屬性正確，你可以直接把功率 sensor 加進去」——它會餵給「即時（Now）」那一頁，讓你看到此刻誰在吃電。但要做日／月統計和成本，還是得有度數。所以官方在個別裝置那一頁給的主力建議，仍然是用積分（Riemann sum integral）把瓦數換成度數。做法在後面的 W 變成 kWh 那一節。
提示：買智慧插座前，先看規格或評測有沒有提到「energy / kWh / 累積用電」。有的話省你一堆設定工。

能源儀表板挑得到的 sensor 長什麼樣

能源儀表板不是「什麼 sensor 都能選」。它會過濾，只列出屬性正確的實體（Entity）。一個 sensor 要被選到，三件事都要對：

屬性要設成什麼白話解釋
device_classenergy / power / gas / water / monetary告訴 HA「這個數字是哪一類東西」
state_class累積型用 total_increasing 或 total；瞬時型（功率）用 measurement告訴 HA「這個數字要怎麼被統計」
unit_of_measurement要在合法清單內，例如 kWh、Wh、W、kW大小寫、上下標都要完全正確

三種 state_class 差在哪

state_class意思典型例子
measurement當下的量測值，不是累積目前功率 850 W、室溫 26 度
total會增加也會減少的累積值雙向電表的淨用電（賣電回去會變小）
total_increasing只會往上加的累積值，偶爾會歸零重來智慧插座的累積用電度數（斷電後從 0 開始）
觀念：官方對 total_increasing 的定義是：值往下掉時，HA 會把它「解讀成新的計數週期開始，或是電表被換掉了」。所以插座斷電歸零不會害你圖表爆掉——HA 知道要怎麼處理。另外它有內建容差，兩次之間掉不到一成不會被當成歸零，避免小數點雜訊誤判。
注意：絕對不要把 device_class: power（瓦）配上 state_class: total_increasing。功率不是累積值，這組合在邏輯上不成立，HA 會在修復（Repairs）裡跳出警告。功率就是 measurement。

怎麼看自己的 sensor 屬性對不對

走 設定（Settings）→ 工具（Tools）→ 狀態（States），搜尋你的 sensor，右邊會顯示它所有的屬性。三個關鍵欄位一次看清楚。同一區還有一個統計（Statistics）分頁，會列出所有有長期統計的實體；某個實體的統計壞掉時，那裡會出現「Fix issue」的連結。

注意：這個地方近期改過兩次名字和位置。它以前叫「開發者工具（Developer tools）」、掛在側欄最下面；後來被搬進設定區，2026 年 8 月的版本又把名字裡的「開發者」拿掉，就叫工具（Tools）——官方說法是不想讓非工程師看到「開發者」就不敢點。網路上舊教學寫「開發者工具」講的都是同一個地方。分頁有 YAML、狀態、動作、範本、事件、統計、Assist 七個，這章會一直回來用它。

用電數據從哪裡來：五種來源

沒有硬體就沒有數據。下面是常見的取得方式，由淺入深。

來源量到什麼難度適合誰
智慧插座 / 智慧開關單一電器的功率，部分機種含累積度數低第一次玩、想抓單一怪獸
CT 夾式電流感測器整條迴路或全戶的功率中想看全屋總量
太陽能逆變器發電量、饋電量中有裝太陽能板
儲能電池系統充電量、放電量中有裝家用電池
瓦斯 / 自來水表用量（m³、L）高要做完整 ESG 盤查

生態系HA 整合要注意什麼

全戶電表這一層

如果你想看的是「整戶」而不是「單一電器」，就得在電箱層級量。做法是把 CT 夾式電流感測器夾在主幹線上，再接到能回報給 HA 的模組（例如支援電力監測的 Shelly 系列，或自己用 ESPHome 做）。

危險：電箱作業有觸電和火災風險。CT 夾雖然是非侵入式（夾在外面不用斷線），但打開電箱、固定線材這些動作請交給合格的電氣技術人員。租屋族動總開關前也要先問房東。這不是可以「試試看」的東西。

太陽能與儲能

多數品牌的太陽能逆變器有自己的 API 或本地介面，HA 有對應的整合可以讀到「目前發電功率」和「累積發電量」。儲能電池則通常會給你「充電累積量」和「放電累積量」兩個數字。設定能源儀表板時，太陽能和電池是兩個獨立的區塊，各自要餵不同的 sensor。

提示：新版的能源設定對感測器格式更寬容了——現在可以直接用「一顆帶正負號的 sensor」來表示市電或電池的雙向流動，也可以用「兩顆各自為正的 sensor」分別代表買電/賣電或充電/放電，不用再自己寫範本（Template）去翻正負號。另外新版也可以幫每個來源自訂名稱，不必忍受「電網用電量」這種罐頭字，改成「總電表」「頂樓太陽能」之類的，多來源的時候好認很多。
提示：如果你有兩顆以上的家用電池，新版可以幫每顆填「容量」，合併後的電量百分比會照容量加權算。不然一顆小電池滿的、一顆大電池空的，平均起來會是很騙人的 50%。

動手做：把能源儀表板開起來

假設你已經有一顆會回報累積度數的插座（例如客廳冷氣那一顆），我們把它變成圖表。

  1. 確認 sensor 合格

    到設定 → 工具 → 狀態，搜尋你的插座 sensor。找那個單位是 kWh、數字只會往上爬的那一顆（不是那顆 W 的）。點開它，確認屬性有 device_class: energy、state_class: total_increasing、unit_of_measurement: kWh。三個都對就過關。

  2. 打開能源設定頁

    走 設定（Settings）→ 儀表板（Dashboards）→ 能源（Energy）→ 編輯儀表板（Edit dashboard）。這裡總共有六種來源可以設：電網（Electricity grid）、太陽能（Solar）、家用電池（Battery storage）、瓦斯（Gas）、自來水（Water）、個別裝置（Individual devices）。

    版本差異提醒：2026 年 3 月起，這個設定頁被拆成電力（Electricity）、瓦斯（Gas）、自來水（Water）三個分頁，六種來源分散在各分頁裡，不再是一長串。舊版本則是全部擠在同一頁。看到的畫面跟這裡不一樣不用慌，要設的東西完全一樣，只是換了擺放方式。

  3. 先加電網用電

    在「電網」區塊選「新增用電量（Add consumption）」，然後從下拉選單挑你的 sensor。如果你的 sensor 沒出現在下拉選單裡，八成是上一步的三個屬性有一個不對，回去看 合格的 sensor 那一節。

  4. 設定電價（可以先跳過）

    加完 sensor 後，同一個對話框會問你要怎麼算錢。想先看度數就選不追蹤成本，之後隨時可以回來補。電價的完整做法在 電價與成本 那一節。

  5. 把單一電器加到「個別裝置」

    如果你想看「冷氣佔了整戶的幾成」，除了電網那一顆總表，再把冷氣那顆 sensor 加到「個別裝置」區塊。這樣儀表板下方會出現各裝置的用電比較。

  6. 存檔，然後去做別的事

    設定完成後，側欄會出現「能源」這個項目。剛設定完打開會是空的，這是正常的。統計資料是以小時為單位累積的，至少等一兩個小時才會看到第一根柱子，等一整天才有像樣的日線圖。

  7. 隔天回來調版面

    有資料之後，在能源儀表板的工具列選「自訂卡片（Customize cards）」，展開各個區塊（總覽 Overview、電力 Electricity、瓦斯 Gas、自來水 Water、即時 Now），用開關切換每張卡片要不要顯示。用不到的區塊關掉，畫面才不會亂。

    順帶一提，能源儀表板的第二個分頁在 2026 年 3 月從「能源（Energy）」改名成「電力（Electricity）」——因為整個儀表板本來就同時管電、瓦斯、水，舊名字容易誤會。

注意：如果側欄根本沒有「能源」這個項目，先確認 configuration.yaml 裡的 default_config: 還在。有些人跟著網路教學把它刪掉了，結果一票內建功能連帶消失。

只有瓦數怎麼辦：用 Riemann sum 積分成度數

這是最常見的狀況：插座只給你 sensor.xxx_power（單位 W），沒有 kWh。能源儀表板選不到它。

解法是內建的積分（Integral / Riemann sum integral）輔助元件。它會不斷去看你的功率 sensor，把「多少瓦 × 持續多久」一段一段累加起來，變成一個新的累積用電 sensor。

觀念：為什麼叫「Riemann sum（黎曼和）」？因為 HA 拿到的不是連續曲線，而是一個一個離散的取樣點。它只能用「把曲線切成很多小塊、每塊算面積再加總」的方式去逼近真正的積分。取樣越頻繁，估得越準。

用介面建立（建議）

  1. 進到輔助元件頁

    設定 → 裝置與服務（Devices & services）→ 輔助元件（Helpers）分頁 → 建立輔助元件（Create helper）。

  2. 選「積分 / Integral」

    清單有點長，用搜尋框打 integ 最快。中文介面可能顯示為「積分感測器」之類的字樣。

  3. 填輸入 sensor

    「輸入感測器」選你那顆單位是 W 的功率 sensor。名稱建議取成看得懂的，例如「客廳冷氣用電量」。

  4. 設定公制前綴與時間單位

    這兩個是關鍵。公制前綴（Metric prefix）選 k，積分時間（Integration time）選 h（小時）。W × h ÷ 1000 = kWh，這樣出來的單位才會是 kWh。前綴選 none 的話你會得到 Wh，數字會大 1000 倍。

  5. 積分方法留預設

    方法（Method）有梯形（Trapezoidal）、左（Left）、右（Right）三種，預設是梯形，官方說在來源更新頻繁時它是目前最準的。除非你很清楚自己在做什麼，不然不要改。

  6. 設定「最大子區間」

    「最大子區間（Max sub-interval）」是給那種「數值不變就不回報」的裝置用的。設一個值（例如 60 秒）之後，就算來源一直沒更新，積分也會照時間往前推進。設 0 代表關閉這個功能。冷氣、除濕機這種會長時間維持固定功率的電器，建議設一個值。

用 YAML 建立

如果你偏好寫檔案，等效寫法是：

sensor:
  - platform: integration
    source: sensor.living_room_ac_power
    name: 客廳冷氣用電量
    unit_prefix: k
    unit_time: h
    method: trapezoidal
    max_sub_interval: "00:01:00"
    round: 3

設定變數的意思：source 是來源實體（必填），unit_prefix 是公制前綴，unit_time 是時間單位，method 是積分方法，round 是小數位數，max_sub_interval 是上面說的強制推進間隔。

注意：積分出來的 sensor 從 0 開始算，它不知道你之前用了多少。所以它跟電費單永遠對不起來，只能拿來看趨勢和比較。要對帳請用真的有累積讀數的硬體。
提示：積分 sensor 的 state_class 固定是 total，不是 total_increasing。這在能源儀表板一樣合法（官方 FAQ 寫的是「total 或 total_increasing 都可以」），所以別看到不是 total_increasing 就緊張。另外它會自動幫你把 device_class 從來源的 power 換成 energy，這個你不用自己設。

Utility Meter：把累積數字切成日／月／季

積分完你會得到一個「從安裝以來一直往上加」的數字。但你真正想知道的是「今天用了幾度」「這個月比上個月多還少」。這就是公用事業計量器（Utility Meter）輔助元件在做的事：它像一個會自動歸零的碼表。

用介面建立

  1. 再開一次輔助元件

    設定 → 裝置與服務 → 輔助元件分頁 → 建立輔助元件 → Utility Meter。

  2. 選輸入 sensor

    選剛剛積分出來的那顆 kWh sensor（或是硬體本來就有的累積 sensor）。

  3. 選歸零週期

    「計量器重置週期」可選每十五分鐘、每小時、每日、每週、每月、每兩月、每季、每年。建議一次建三個：日、月、年，各自命名清楚。

  4. 視情況打開「週期性歸零」

    如果來源 sensor 會自己歸零（例如智慧插座斷電重來），要確認「週期性歸零（Periodically resetting）」是開啟的，這樣 Utility Meter 才知道要怎麼處理那個掉下去的數字。這個選項預設是開啟的。

  5. 需要的話設偏移

    「計量器重置偏移（Offset）」可以把週期的起點往後推。例如你的電費單是每月 5 號結算，就把月週期的偏移設成 4 天，讓 HA 的月份跟帳單對齊。

YAML 寫法

utility_meter:
  ac_daily:
    source: sensor.living_room_ac_energy
    name: 客廳冷氣 今日用電
    cycle: daily
  ac_monthly:
    source: sensor.living_room_ac_energy
    name: 客廳冷氣 本月用電
    cycle: monthly
  ac_yearly:
    source: sensor.living_room_ac_energy
    name: 客廳冷氣 今年用電
    cycle: yearly

可用的設定變數包含 source、name、unique_id、cycle、offset、cron、delta_values、net_consumption、tariffs、periodically_resetting、always_available。其中 delta_values 預設 false（來源是絕對讀數而非增量）、net_consumption 預設 false（只算正向）、periodically_resetting 預設 true。

注意：官方明講「每個 sensor 的第一個週期都是不完整的」。你在星期三中午建立的「本週用電」，那一週的數字沒有意義，從下週一開始才是完整資料。做報告記得跳過第一個週期。

Utility Meter 也會產生動作

它提供兩個動作（Action，舊稱服務 Service）：

動作用途
utility_meter.calibrate把計量器校正成指定的數值
utility_meter.reset把計量器歸零

設定好之後這些 sensor 是跨重開機保存的，HA 重啟不會把你的月累積吃掉，可以放心。

電價與成本追蹤

有了度數，乘上電價就變成錢。錢比度數有說服力得多——跟老闆講「我們一年多花了 8000 塊在待機電力上」，比講「多用了 200 度」有效。

三種算錢的方式

在能源設定頁把某個用電來源加進去之後，HA 會問你要怎麼追蹤成本，選項大致是這三類：

方式怎麼運作適合誰
固定單價你直接填一個「每度多少錢」的數字，HA 全程用它乘絕大多數人。想快速看到大概數字就選這個
用一個實體代表當前單價指定一個 sensor，它的值就是「現在每度多少錢」。單價變了，成本就跟著變有分時電價，或電價會隨時間浮動的人
用一個實體代表總金額你自己算好累積金額，HA 直接拿來用已經有現成金額 sensor 的進階玩家
觀念：選了成本追蹤之後，HA 會自動幫那個能源來源生出一個對應的「成本」統計，你不用自己建。之後儀表板上就會同時顯示度數和金額。

台灣電價要注意的事

台灣住宅用電有兩個特性讓「一個固定單價」不太準：

  • 累進級距：用越多，超出部分的單價越高。你的平均單價會隨著當月用量往上飄。
  • 夏月／非夏月：夏季月份的費率跟其他月份不一樣。
注意：費率級距、夏月定義與各級單價會調整，這章刻意不寫任何具體數字，因為印在教學裡的數字一定會過期。請直接查台灣電力公司官網的最新電價費率表，或翻你自己的電費單背面。填進 HA 的時候用你查到的數字。
提示：務實的做法是：拿你最近一期電費單的「總金額 ÷ 總度數」，得到一個平均單價，填進去當固定單價。這個數字不精確，但它反映的是你自己的真實用電結構，拿來做「這個月比上個月省了多少錢」的比較完全夠用。每隔幾個月更新一次即可。

分時電價（時間電價）怎麼做

如果你申請了時間電價，尖峰和離峰單價不同，做法是用 Utility Meter 的費率（Tariffs）功能：

utility_meter:
  home_daily:
    source: sensor.home_energy
    name: 家庭 今日用電
    cycle: daily
    tariffs:
      - peak
      - offpeak
  home_monthly:
    source: sensor.home_energy
    name: 家庭 本月用電
    cycle: monthly
    tariffs:
      - peak
      - offpeak

這樣會產生 sensor.home_daily_peak、sensor.home_daily_offpeak、sensor.home_monthly_peak、sensor.home_monthly_offpeak 四個 sensor，再加上 select.home_daily 和 select.home_monthly 兩個選擇器（Select）實體，用來切換「現在算哪一段費率」。

注意：注意 home_daily 這個最上層的 key 才是實體 ID 的來源，name 只影響畫面上顯示的名字。所以 key 一律用英數底線（像 home_daily），不要用中文；中文 key 會讓你之後在自動化裡打不出實體 ID。這就是第 4 章講的「顯示名稱可以中文，實體 ID 一定要英文」。

接著寫一個自動化，在切換時間點去改那個 select：

alias: 切到尖峰費率
triggers:
  - trigger: time
    at: "16:00:00"
conditions:
  - condition: time
    weekday:
      - mon
      - tue
      - wed
      - thu
      - fri
actions:
  - action: select.select_option
    target:
      entity_id: select.home_daily
    data:
      option: peak
mode: single

再寫一個對應的「切回離峰」自動化即可。切換時間、平日假日規則請以你申請的電價方案為準。

注意：如果你有多個 Utility Meter 都設了費率，記得每一個的 select 都要切。漏掉一個，那個計量器的分段資料就會錯。可以在同一個自動化的 entity_id 裡一次列出多個實體。

瓦斯與自來水：ESG 盤查的另外兩隻腳

如果你只是想省電費，看到這裡就夠了。但要做完整的 ESG 或永續盤查，用電只是其中一項，瓦斯和水也要算。

能源儀表板本身有獨立的「瓦斯」和「自來水」區塊，設定邏輯跟電一模一樣：要有一個累積型的 sensor，device_class 設成 gas 或 water，state_class 用 total_increasing 或 total，單位用體積單位。加進去之後一樣可以設單價來換算成錢。

難的是硬體。台灣的瓦斯表和水表大多沒有現成的智慧介面，官方文件列的幾種常見做法是：

做法原理難度
影像辨識模組用小鏡頭對著錶面拍照，在裝置端跑辨識把數字讀出來中，要固定鏡頭和光源
磁力感測器膜式瓦斯表內部有轉動的磁鐵，用磁力計偵測轉動次數中高，要找到對的位置
簧片開關（Reed switch）偵測錶內磁鐵每轉一圈觸發一次，換算成用量中，不是每種錶都有這個磁點
無線電接收（RTL-SDR）有些電、瓦斯、水表會用無線協定定期廣播讀數，用一支便宜的 USB 電視棒就能收高，要看你當地的表有沒有在廣播
智慧電表通訊埠（P1）部分國家的電表有標準化的資料輸出埠可以直讀，順便連瓦斯用量一起吐出來低，但這是荷蘭、比利時、盧森堡那邊的規格，台灣一般住宅用不到
危險：瓦斯表絕對不要拆、不要動內部、不要在旁邊做會產生火花的東西。所有可行的做法都是「從外面觀察」，不碰管線本身。有任何疑慮就不要做，改用人工每月抄表填進 HA。
提示：做不到自動抄表也沒關係。建一個「數字（Number）」輔助元件，每個月自己把帳單上的度數填進去，一年下來也是十二個資料點，足以畫趨勢圖、寫進報告。手動資料不丟臉，沒資料才丟臉。

ESG 敘事：把數據變成一份說得出口的報告

數據本身不會說服人，對照才會。這一節講怎麼把儀表板上的圖變成一個有頭有尾的故事。

第一步：建立基線（Baseline）

什麼都先不要改，讓系統跑滿一個完整週期——最少兩週，最好一個月。這段期間的數字就是你的「基線」，是之後所有改善的比較對象。

注意：基線期間不要動任何節能措施。很多人一裝好就開始關這關那，結果沒有乾淨的對照組，後面說不清楚到底省了多少。忍住。

第二步：找出吃電怪獸

不用高深技巧，看三個地方：

看哪裡找什麼常見的兇手
個別裝置排行誰的總度數最大冷氣、除濕機、電熱水器
凌晨時段的用電大家都睡了還在跑的是什麼飲水機保溫、機上盒、NAS、老冰箱
每日曲線的形狀有沒有該降沒降的平台忘記關的除濕機、待機功耗高的設備
觀念：「凌晨用電」是最好用的一招。半夜三點的用電量幾乎就是你家的待機基礎負載。把這個數字乘上 24 小時再乘 30 天，你會嚇到——那是你什麼都沒做就要付的錢。降低它的投資報酬率通常最高。

第三步：辦公室常見的改善措施

  • 茶水間熱水器排程：用第 8 章學的自動化，讓熱水器只在上班時段通電。週末和連假整整兩到三天的保溫電力直接省掉。
  • 下班自動斷電：影印機、螢幕、桌上型設備接在智慧插座上，晚上十點統一關閉。
  • 冷氣設定溫度控管：不用真的去改冷氣，先量。把「冷氣用電」跟「室外溫度」放在一起看，就能算出調高一度到底省多少。
  • 異常用電通知：設一個自動化，當非上班時間的總功率超過某個門檻就推播通知（做法看第 7 章）。這招常常會抓到「有人忘了關」。

第四步：寫成報告

一份能用的節能報告只要這幾段，不用寫得像論文：

  1. 量測方法

    寫清楚你量了哪些迴路或哪些裝置、用什麼設備量、資料期間從哪天到哪天。誠實寫出沒量到的部分（例如「未涵蓋照明迴路」），這反而增加可信度。

  2. 基線數據

    改善前的月用電量、日平均、待機基礎負載。附上能源儀表板的月檢視數字。

  3. 採取的措施

    一條一條列，每條寫「做了什麼」「什麼時候開始」。有自動化的話寫出觸發條件，這是你的執行證據。

  4. 改善後數據與對照

    同樣期間長度的用電量，跟基線並排。用絕對值（省了幾度）和百分比（省了幾成）兩種寫法，並附上金額換算。

  5. 誠實標註干擾因素

    「本期為非夏月，氣溫較低，部分降幅來自季節因素」——寫出這句話的報告，比看起來完美的報告可信一百倍。

提示：要導出原始數字的話，能源儀表板的圖表可以切換到不同時間範圍逐一抄，或是在歷史（History）頁面查詢對應的 Utility Meter sensor。如果需要大量匯出，社群有一些統計匯出的自訂元件，但那已經超出這章範圍。

進階：裝置排行與太陽能自發自用率

個別裝置耗電排行

把每一顆插座的 kWh sensor 都加進能源設定的「個別裝置」區塊，儀表板就會自動幫你排出誰吃最多。

如果同一條迴路上既有總表也有子裝置，會發生重複計算——總表已經包含了子裝置的用量。官方提供了「上游裝置（upstream device）」的設定來處理這件事：你可以把某個裝置指定為另一個裝置的上游，形成階層。

注意：要設階層，必須先把所有相關的實體都加進「個別裝置」清單。只有已經在清單上的裝置，才會出現在「上游裝置」的下拉選單裡。順序搞反就會找不到選項。

即時功率分布

新版加入了「分布卡片（Distribution card）」，會用一條橫向的比例長條圖顯示多個實體之間的數值分布，還附互動式圖例——點圖例上的項目，百分比會即時重算。拿它來擺一排功率 sensor，就能一眼看出現在這一刻是哪個迴路或哪台電器在吃電。這對抓「突然跳電是誰害的」特別好用。

注意：這張卡片會檢查你放進去的實體「單位和類型合不合得起來」。把 W 和 kWh 混在同一張卡裡它不會讓你過——要嘛全放功率，要嘛全放用電量，不要混。

能源儀表板自己的「即時（Now）」那一頁也一直在長東西：現在頂端有徽章（badge）直接顯示當下的用電功率、瓦斯流量、用水流量；水也有了自己的桑基圖（Sankey chart），跟電力那張一樣，可以看出水是流去哪些地方。想快速看「現在誰在跑」，這一頁比自己拼卡片快。

太陽能自發自用率

有太陽能的話，你會關心一個指標：發出來的電，有多少是自己用掉的（自發自用），有多少賣回電網。

能源儀表板本身在設好太陽能來源後，就會顯示發電量與電網進出的關係。想要一個明確的百分比，可以用範本 sensor 自己算——概念是「（總發電量 − 饋電量）÷ 總發電量」：

template:
  - sensor:
      - name: "太陽能自發自用率"
        unique_id: solar_self_consumption_ratio
        unit_of_measurement: "%"
        state_class: measurement
        availability: >
          {{ is_number(states('sensor.solar_production_monthly'))
             and is_number(states('sensor.grid_export_monthly'))
             and states('sensor.solar_production_monthly') | float(0) > 0 }}
        state: >
          {% set gen = states('sensor.solar_production_monthly') | float(0) %}
          {% set exp = states('sensor.grid_export_monthly') | float(0) %}
          {{ ((gen - exp) / gen * 100) | round(1) }}

把 sensor.solar_production_monthly 和 sensor.grid_export_monthly 換成你自己的月度 Utility Meter sensor。availability 那段是防呆，避免來源還沒就緒或發電量為零時整個 sensor 變成錯誤值。

提示：這個百分比不要設 device_class。百分比不是能源、不是功率，硬套一個 device_class 反而會讓 HA 抱怨。只給 unit_of_measurement: "%" 和 state_class: measurement 就好。

資料要留多久

很多人擔心「我的資料庫會不會爆掉」。這裡要分清楚兩件事：

類型存什麼保留多久
記錄器歷史（Recorder history）每一次狀態變化的完整明細由 purge_keep_days 控制，預設 10 天
長期統計（Long-term statistics）彙總後的統計值（能源儀表板用的就是這個）不隨一般歷史清除而消失，可以看很久以前的月報
觀念：所以「歷史頁面只剩十天」是正常的，但你的能源儀表板還是看得到去年同月。兩者來源不同。想調整明細保留天數請看記錄器（Recorder）的設定，但不要為了看能源報表而把它調到很大，那只會讓資料庫肥大。

常見卡關

  1. 能源設定的下拉選單裡選不到我的 sensor

    九成是屬性不合格。到設定 → 工具 → 狀態（舊版叫「開發者工具」）檢查三件事：device_class 是不是 energy（或 gas / water）、state_class 是不是 total_increasing 或 total、unit_of_measurement 是不是合法單位（kWh 的大小寫要完全正確，KWH、kwh 都不算）。另外你選到的可能是那顆 W 的功率 sensor，不是 kWh 的用電量 sensor——這兩顆名字常常只差一個字。

  2. 某一天的用電量突然暴衝到幾千度

    典型症狀是來源 sensor 歸零之後又被當成「持續累積」，或是 state_class 選成 total 但裝置其實會歸零，HA 把「從 0 跳回大數字」算成一次巨大的增量。
    治本：把該 sensor 的 state_class 改成 total_increasing；如果是走 Utility Meter，確認「週期性歸零」是開啟的。
    治標：到設定 → 工具 → 統計，找到那個實體，用日期時間欄位把那個爆掉的資料點搜出來，直接把值改回合理數字。這一頁就是官方拿來修統計的地方，實體有問題時它旁邊還會出現「Fix issue」連結。

  3. 設好了但儀表板一直空白

    先確認你有沒有等夠久。統計是以小時為單位寫入的，剛設定完當然空白，至少等一兩小時。再來確認側欄真的有「能源」項目——沒有的話檢查 configuration.yaml 的 default_config: 有沒有被刪掉。最後確認來源 sensor 現在有沒有在動，如果它卡在 unavailable 或 unknown，那是裝置連線問題，不是儀表板問題。

  4. Repairs 跳出「state class 與 device class 不相容」

    最常見的是把 device_class: power 配上 total_increasing。功率是瞬時值，只能用 measurement。如果 sensor 是整合提供的，去該整合或裝置韌體回報；如果是你自己寫的範本 sensor，直接改你的 YAML。

  5. 積分出來的數字大 1000 倍或小 1000 倍

    公制前綴（unit_prefix）跟時間單位（unit_time）沒配對好。從 W 積分成 kWh，前綴要 k、時間要 h。前綴留空會得到 Wh。發現設錯就把那個輔助元件刪掉重建，改設定不會回頭修正已經累積的舊資料。

  6. 電器明明在跑，積分 sensor 卻不動

    來源功率 sensor 可能「數值沒變就不回報」。積分要有新的取樣點才會前進。到那個積分輔助元件的設定裡把「最大子區間（Max sub-interval）」設一個值（例如 60 秒），強制它按時間推進。

  7. Utility Meter 的第一個月數字很奇怪

    這是預期行為，官方明講第一個週期一定不完整。等下一個完整週期開始再看。做報告時把第一個週期整段捨棄。

  8. 成本一直顯示 0

    檢查你在能源設定裡有沒有真的選了成本追蹤方式（預設是不追蹤的）。如果選了「用一個實體代表當前單價」，去確認那個單價 sensor 現在有沒有正常的數值，它如果是 unknown，乘出來自然是 0。另外成本統計跟用電量一樣要等一小時才會出現第一筆。

常見問題

我一定要買硬體嗎？能不能用估算的？
可以估算，但不要拿估算值去做對外報告。做法是用第 12 章提過的方式，寫一個範本 sensor：當某個開關是 on 時輸出該電器的標稱功率，off 時輸出 0，再拿去積分。這對「這台燈具大概吃多少」夠用，但它假設電器永遠以標稱功率運作，冷氣、冰箱這種功率會變的機器誤差非常大。要拿數字說服人，還是要真的量。
能源儀表板的數字跟台電帳單對不起來，是不是我設錯了？
大多數情況下不是設錯。原因有幾個：一，你量的通常只是部分迴路或部分電器，不是全戶總表；二，Riemann sum 是逼近，取樣頻率不夠高就會有誤差；三，計費週期不一致——台電是兩個月一期、有自己的抄表日，HA 預設是自然月。第三點可以用 Utility Meter 的「偏移（Offset）」去對齊。

把能源儀表板當成趨勢工具而不是對帳工具，心態會健康很多。它的價值在「這個月比上個月少了兩成」，不在「跟帳單分毫不差」。
「積分」跟「Utility Meter」到底該用哪一個？我兩個都要建嗎？
它們解的是不同問題，很多情況兩個都要。

積分（Integral）：把「瓦（W）」變成「度（kWh）」。只有在你的裝置沒有累積用電量、只有瞬時功率時才需要。
Utility Meter：把「一直累加的度數」切成「今天 / 這個月 / 今年」。輸入本身就已經是 kWh 了。

所以流程是：功率 →（積分）→ 累積度數 →（Utility Meter）→ 日月年分段。如果你的插座本來就給累積度數，跳過積分，直接接 Utility Meter。
我把 sensor 改名或換了新插座，之前的歷史數據會不會不見？
統計資料是綁在實體 ID（entity_id）上的。只改顯示名稱不影響歷史。改實體 ID 的話，HA 通常會問你要不要一併搬移統計資料，選「是」就會保留。

但如果你是換了一台實體裝置，那就是全新的實體、全新的計數，舊資料還在舊實體上，但新舊接不起來，圖表會有斷點。所以命名在一開始就要想清楚——這正是第 4 章一直在強調的事。要換裝置前，先把舊資料的月統計數字抄下來備份。
設了一堆 sensor，會不會把我的 SD 卡或硬碟寫爆？
會有影響，但沒有想像中嚴重。功率 sensor 因為變化頻繁，是寫入量最大的類型。幾點建議：一，記錄器（Recorder）的明細預設只留 10 天，這已經是很克制的設定，不要隨便調大；二，長期統計是彙總過的，體積小很多，不用擔心；三，真的在意的話，用 Recorder 的設定把你不需要看明細的高頻 sensor 排除掉，統計還是會照常記。

另外，如果你還在用 SD 卡跑 HA 又要長期記錄能源資料，建議認真考慮換成 SSD。SD 卡壽命對頻繁寫入很不友善。備份的事請看第 9 章。
我沒有太陽能也沒有電池，只有幾顆插座，這套還有用嗎？
非常有用，而且這才是大多數人的起點。三顆插座就能做出很有價值的東西：一顆接冷氣、一顆接除濕機、一顆接你懷疑的老電器。跑一個月，你會很清楚地看到誰是主角。

能源儀表板的「個別裝置」區塊本來就是為這個情境設計的，你不需要全戶電表也能用。等你摸熟了、確定這件事對你有價值，再往上做全戶量測也不遲。
資料要累積多久才能開始下結論？
看你要下什麼結論。

「哪台電器最吃電」：一週就能看出大概，兩週相當可靠。
「我的節能措施有效」：至少要改善前一個月、改善後一個月，而且要注意季節干擾——拿七月跟十月比，降幅有一大半是天氣的功勞，不是你的。理想是拿今年某月跟去年同月比，但那要等一年。
「年度總量」：老實說就是要一整年。第一年先把資料收好，第二年才有得比。
