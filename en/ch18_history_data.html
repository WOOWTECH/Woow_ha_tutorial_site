Chapter 18

History, Recorder, and data export

Home Assistant records state changes in the background. Learn where that history is stored, how long it is retained, how to export it to CSV, and how to keep the database from filling your storage.

Why this matters

Once your devices and automations are running, you will almost certainly encounter two situations:

First: You want to know who left the porch light on last Wednesday night, or how much energy the air conditioner used this month. Data from three days ago is available, but data from three months ago is gone—even though last year’s energy use is still visible. This is intentional, and this chapter explains why.

Second: Home Assistant becomes unusually slow: a light takes three seconds to respond, and a restart takes ten minutes. An oversized database is a common cause. On a Raspberry Pi that uses a microSD card, sustained database writes can also shorten the card’s life.

Concept: Home Assistant manages both current state and historical data. Managing that history well is essential to a stable system.

After reading this chapter, you will have these abilities:

  • Choose between History and Activity (formerly Logbook) for a given question.
  • Identify where Recorder stores data, how long it retains detailed history by default, and what affects database size.
  • Use include and exclude to keep noisy entities out of Recorder.
  • Export CSV data for analysis in Excel or Google Sheets.
  • Purge an oversized database, respond safely to corruption, and choose a long-term storage option.

Chapter 9 covers general backup practices; this chapter focuses on how the database affects backups. See entity_id conventions in Chapter 4 for entity naming used in the filtering examples.

History and Activity answer different questions

The sidebar contains two similar entries: History and Activity. They answer different questions.

Warning: Activity was named Logbook before Home Assistant 2025.10. The UI label changed, but the integration name and YAML block remain logbook. Older instructions that mention Logbook refer to the same feature.
Question Where to look Why
“How did the living-room temperature change over the past three days?” History History plots numeric values as a line chart for trend analysis.
“How many hours was the entry light on yesterday?” History History shows switch entities as timelines, making their active periods easy to see.
“Who just turned off the air conditioner?” Activity Activity records the user or automation responsible.
“What happened at 3:00 a.m.?” Activity Activity lists events in reverse chronological order.
“Did this automation run?” Activity An automation trigger leaves an entry in Activity.

Think of History as a chart in a medical record and Activity as a shift log. History shows how values changed; Activity shows who or what performed an action.

One practical difference is that Activity omits sensors with units by default. Temperature, humidity, and power sensors can update every few seconds and would overwhelm the event list. View those sensors in History instead.

Tip: Both pages use Recorder data. Excluding an entity from Recorder removes it from both History and Activity.

Recorder: the source of all history

History and Activity are views; they do not store data themselves. The Recorder integration writes state changes to storage.

You usually do not install Recorder separately. History relies on Recorder, and both use the same database settings. A new installation enables them through configuration.yaml with default_config:.

Which file stores the data?

By default, Home Assistant uses SQLite, the database is a file in the settings folder:

/config/home-assistant_v2.db

This single file contains the default Recorder database. Because it is stored beside configuration.yaml, a full backup normally includes it.

Default retention period

Recorder’s purge_keep_days setting defaults to 10 days. Detailed state changes older than that are deleted automatically.

It is accompanied by two switches that are turned on by default:

Options Default value what is it doing
purge_keep_days 10 How many days to keep transaction history
auto_purge true Delete expired data automatically at 04:12 local time each morning.
auto_repack true Reorganize the database every second Sunday so freed space is returned to storage.
commit_interval 5 Write accumulated changes to the database every few seconds
Concept: commit_interval batches changes in memory before writing them to storage. The default is 5 seconds. Increasing it, for example to 30, reduces writes but can lose up to that interval of data during a power failure.

How big will the database be?

Database size depends on both the number of entities and how often they change. Use these examples only as rough guidance:

situation Approximate scale reasonable expectations
A few lights and temperature/humidity sensors 20 to 50 entities Usually tens of MB
A typical home with contact, occupancy, and appliance sensors 100–300 entities Hundreds of MB is common
Smart meter, solar, or second-by-second power monitoring High-frequency numeric sensors May reach several GB and grow quickly

The key question is how many times each entity changes per day. A light may change 6 times, while a power sensor that reports every second can create tens of thousands of rows. One such sensor can generate more data than all other entities combined.

Use these two views to check current storage use:

What you want to see how to go see what
Free space on the system Settings → System → Storage Point to the usage bar to see remaining-space details.
Estimated database size Settings → System → Repairs → three-dot menu → System information Find Estimated database size under Recorder; the value is shown in MiB.

The later SQL integration section shows how to expose database size as a sensor on your dashboard.

Warning: Page locations and field names can vary by version. Follow the labels in your installation. If needed, search Settings for “storage” or “system.”

Long-term statistics: why energy lasts longer than switch history

Detailed history and long-term statistics have different retention rules.

Detailed history defaults to 10 days, yet the Energy dashboard can still show last year’s consumption. Home Assistant stores these as two different types of data.

Short-term history (states) Long-term statistics
Stored data Every state change Hourly summaries
Resolution Original timestamps and values Hourly minimum, maximum, average, or change
Retention 10 days by default Not removed by the normal history purge
Eligible entities All entities not excluded from Recorder Only entities with a supported state class
Rows per day Depends on update frequency; potentially tens of thousands 24 hourly summaries

The states table records individual changes. Statistics compress those changes into fixed-interval summaries, producing only 24 hourly rows per day and making multi-year retention practical.

Which entities will have long-term statistics?

Only entities with a supported state_class enter the statistics table. Chapter 17 explains each state class; here the focus is retention:

status category What can be saved in statistics for you? Example at home
measurement Hourly minimum, maximum, average Living room temperature, room humidity, and current power of air conditioner
total / total_increasing Change during each period Cumulative electricity or water-meter readings
No status category Nothing is saved, only the transaction records of the past 10 days Turning on/off lights, opening/closing doors and windows, whether people are at home or not

An energy meter with total_increasing retains long-term statistics. A light’s nonnumeric on/off state has no state class, so only its detailed history remains, for 10 days by default.

Concept: Home Assistant creates short-term statistics every 5 minutes, then compiles them into hourly long-term statistics. Short-term data is purged regularly; hourly long-term statistics remain.

This also explains why older History charts can look smoother and lose brief peaks. Within the detailed-history window, the chart uses full-resolution Recorder data; beyond it, the chart uses hourly long-term statistics. An hourly average will not exactly match any single reading. Home Assistant displays higher-resolution lines in a darker shade.

Tip: For values you need to retain for years, such as water or gas readings, do not simply increase purge_keep_days. Confirm that each entity has the correct state class and unit so Home Assistant can generate long-term statistics.

DIY: Download history to CSV

Home Assistant can export History data to CSV without additional software.

  1. Open "History" in the sidebar

    If you can't see the sidebar, click your name at the bottom of the sidebar to enter the profile page and confirm whether it is hidden; or the fastest way - directly follow the address bar /history press Enter.

  2. Select the area, device or entity you want

    Use the selector at the top to choose an area, device, or entity. Selecting an area shows the charts for its entities, provided that you assigned areas as described in Chapter 3.

  3. Set time range

    Select Today, This week, or custom start and end dates. The selected range determines the amount of CSV data. Start with one day to confirm the export before requesting a large range.

  4. Click "Download data" in the upper right corner

    The button is in the upper right corner of the page, and the English interface says Download data, localized interfaces use the corresponding translated label. Click on the browser and it will save a CSV file directly to your download folder without any setting window popping up.

  5. Open it in a spreadsheet

    Open the file in Excel, Numbers, or Google Sheets. If non-Latin text is garbled, use the application’s import command and select UTF-8 instead of opening the file directly.

Warning: The download reflects the data available to History. Outside the detailed retention period, eligible sensors use hourly statistics. CSV export cannot recover second-by-second data that Recorder has already purged.
Tip: If you are doing homework or reporting, this method is very useful: select a temperature sensor, capture the range for a week, download the CSV, and paste it into a spreadsheet to draw a "weekly room temperature change graph." If you want to grasp the long-term trend, choose a numerical sensor with statistics. If you extend the time for one year, you will get an hourly average, which will look better when drawn.

Export Activity events

Starting with Home Assistant 2026.8, Activity provides CSV download and a Clear and reset action. Choose the export that matches the data you need:

Information needed Where to download it Result
Value change curve (temperature, electricity consumption, humidity) "Download data" in the upper right corner of the history page Time + value, suitable for drawing
Event journal (who opened it, which automation ran it) CSV download of event page Event record one by one, suitable for tracing
Warning: The release notes mention Activity’s Clear and reset action without fully defining its scope. Read the confirmation prompt before proceeding. For controlled database cleanup, prefer recorder.purge, described later in this chapter.

Tools → Statistics: Fix those skewed numbers

Open Settings → Tools. Its tabs include YAML, States, Actions, Templates, Events, Statistics, and Assist.

Warning: This area was named Developer tools and appeared in the sidebar before Home Assistant 2026.2. It moved under Settings, then became Tools in 2026.8. Older instructions refer to the same area.

The Statistics page only does two things, but both are critical.

1. It will list problematic statistical entities

The page will list all entities with "long-term statistics" and mark the "Fix issue" links on the ones with problems. Clicking on them will tell you what problems were detected. The two most common ones are:

Symptoms plain-language explanation How to usually deal with it
Unit changed The sensor previously reported W and now reports kW, making the existing statistics incompatible. Follow the prompt to convert or retain compatible data, or clear the old statistics and start over.
State class no longer supports statistics After an integration update, the entity no longer generates statistics. Follow the prompt to remove obsolete statistics if you no longer need them.
The entity no longer exists The device was dismantled and renamed, but the statistics remain Make sure you really don’t want it and then clear it.

2. It can directly change the value of a certain hour

This tool can correct an isolated, invalid reading. For example, a meter might jump to 999999 kWh and flatten the rest of the month’s Energy chart. See Chapter 17 for energy statistics.

The operation described in Home Assistant documentation is: click the icon next to the entity on the statistics page, use the date and time fields to find the data point, and then change the value.

  1. First find the point in time when the problem occurred on an energy or historical graph

    Move your mouse over the unreasonable pillar and write down the date and hour.

  2. Go to Settings → Tools → Statistics and find the entity

    It is faster to type in the entity name using the search box above.

  3. Open the adjustment interface and locate the record by date and time

    It displays the value recorded for that hour.

  4. Change it to a reasonable value, save it and go back to look at the display.

    Charts often require a page refresh to reflect.

Danger: This edits statistics already stored in the database, with no undo button. Make a backup first as described in Chapter 9. An adjustment to a cumulative sensor can affect later calculations, so review the complete curve afterward.

Use include/exclude to streamline information

An oversized database is usually caused by high-frequency entities you never review, not by ordinary lights. Start by telling Recorder not to store unnecessary data.

Write these settings in configuration.yaml, run a configuration check, and restart Home Assistant for them to take effect.

Method A: Exclude selected data (recommended for beginners)

Record everything by default, then exclude only known noisy data. This approach reduces the chance of omitting important history.

recorder:
  purge_keep_days: 10
  exclude:
    domains:
      - automation
      - update
    entity_globs:
      - sensor.sun*
      - weather.*
    entities:
      - sensor.date
      - sensor.last_boot
    event_types:
      - my_custom_event

Method B: Include selected data (for tightly controlled databases)

This reverses the default: Recorder stores only the data you name. It offers the most control, but can easily omit history you later need.

recorder:
  include:
    domains:
      - sensor
      - switch
      - media_player
  exclude:
    entities:
      - sensor.last_boot
      - sensor.date
    entity_globs:
      - sensor.weather_*

You can combine the two: use include for a broad set, then exclude for exceptions. The complete precedence rules are in the Home Assistant documentation. In general, more specific rules take priority: explicit entities outrank globs, and globs outrank domains.

Four filter conditions

Conditions Scope Writing examples
domains entire category - automation
entities Designate a single entity - sensor.last_boot
entity_globs Wildcard patterns for groups of entities - sensor.phone_*
event_types Event (not entity) - call_service

Common sources of excessive writes

Type why noisy Should we exclude
Mobile-app battery, bearing, and step sensors They can change frequently and may have little historical value Consider excluding sensors you do not review
Power sensors reporting every second One entity can occupy most of the database Keep only when needed, or purge its detailed history after a few days
update domain (firmware update notices) No historical value Recommended to exclude
Sun azimuth, weather forecast details Continuous change, no need for history Recommended to exclude
The state of the automation entity itself What you want is "did you run?" That's in the activity can be excluded
Contact, occupancy, light, and lock entities They change infrequently and can be valuable during investigations Generally retain
Warning: Exclusion rules affect only future writes. They do not delete existing database rows. To apply new filters to old data, use recorder.purge with apply_filter enabled as described next.
Danger: Excluding an entity removes it from History, Activity, the Energy dashboard, and future long-term statistics. Do not exclude energy meters used by the Energy dashboard. Missing energy data cannot be reconstructed later.

Purge stored data safely

Filtering reduces future growth but does not shrink existing data. Recorder provides these actions (formerly called services):

action what to do
recorder.purge Clear old data older than a specified number of days
recorder.purge_entities Only clear specified entities/categories/wildcards
recorder.disable Pause recording
recorder.enable Resume recording
recorder.get_statistics Read out long-term statistics

Three parameters of recorder.purge

parameters Default meaning
keep_days Recorder configuration value Number of recent days to retain
repack false Rewrite the entire database and really return the space to the hard disk
apply_filter false Apply to old data together with include / exclude in the configuration file

After adding exclusion rules and restarting Home Assistant, this combination removes old rows that now match the filters and repacks the database:

action: recorder.purge
data:
  keep_days: 7
  repack: true
  apply_filter: true

Open Settings → Tools → Actions, select recorder.purge, switch to YAML mode, paste the example, and run it. In older versions, this area was named Developer tools and appeared in the sidebar.

Warning: repack is resource intensive. Home Assistant may slow down, and the process temporarily requires additional disk space. The documentation recommends free space at least equal to the database size. If storage is nearly full, remove unneeded backups or other files before repacking.

Only clear a certain entity that is noisy

If one power sensor is causing the growth, do not purge unrelated history. recorder.purge_entities accepts entity_id, domains, or entity_globs. Its keep_days default is 0, which deletes all matching data.

There is a very practical automation example in Home Assistant documentation: only the data of the socket for the last 5 days will be retained every morning.

alias: Clear old data from noisy power sensors every day
triggers:
  - trigger: time
    at: "04:15:00"
actions:
  - action: recorder.purge_entities
    data:
      keep_days: 5
      entity_id: sensor.power_sensor_0
mode: single

The advantage of this way of writing is that you retain the ability to see the curve in recent days without letting it accumulate infinitely. And because long-term statistics are not affected, if this sensor has a status category, the annual trend can still be seen.

Tip: Recorder actions require Administrator privileges. If you are signed in as a standard user created in Chapter 5, switch to an Administrator account.

The default auto_purge runs at 04:12 each morning, so manual purging is normally unnecessary. Use it after changing filters when you need them applied to old data, or when urgent database cleanup is required.

Does the backup include the database? How to save the database if it is broken?

Full backups include the database

Because home-assistant_v2.db is in the configuration folder, a full backup normally includes it. A large database therefore increases every full backup. A 2 GB database included in three retained backups can consume about 6 GB, before accounting for other backup content or compression.

To reclaim storage, purge unneeded database rows, filter unnecessary Recorder data, and reduce purge_keep_days if appropriate. Also set backup-retention limits and keep an independent copy outside the Home Assistant host.

Warning: Backup options for media, shared folders, and the database vary by Home Assistant version. Follow the options shown in your installation. Reducing unnecessary database growth remains effective regardless of those interface differences.

Use this order: configure exclusions → restart Home Assistant → run recorder.purge with repack → create a new backup.

Changing databases does not migrate existing history

Danger: Home Assistant warns that changing Recorder databases can make existing history unavailable, and database migration is not officially supported. Plan a switch from SQLite to MariaDB as a new history baseline. If you intend to switch, do it before accumulating years of data.

Symptoms and treatment of database corruption

Common causes of SQLite corruption include a power failure during a write and failing storage. Home Assistant may still open, while History and Activity are empty and the logs contain database errors.

  1. Confirm the diagnosis

    Open Settings → System → Logs and look for errors containing sqlite or database.

  2. Know that Home Assistant will save itself

    If SQLite is irreparably damaged, Home Assistant moves the damaged database aside and creates a new one. Your settings, automations, and devices remain intact; the unavailable data is history.

  3. Make sure there is enough disk space

    Home Assistant recommends free space of about 2.5 times the database size when recovering a damaged SQLite database. Recovery may fail without enough space.

  4. Accept historical losses and find root causes

    Follow the linked SQLite recovery guidance if the history is important. Otherwise, preserve the damaged .db file for later analysis, allow Home Assistant to start a new database, and address the cause: failing storage or unsafe power removal.

Tip: Recorder database corruption generally affects history, not device control or automations. Confirm system behavior and logs before taking destructive action.

Advanced 1: Switch from SQLite to MariaDB

SQLite is a simple, zero-configuration, single-file database. With many entities and frequent writes, a database server may offer better performance.

Home Assistant document lists the minimum supported version:

Database Minimum version Suitable for whom
SQLite 3.40.1 By default, most people don’t need to touch it
MariaDB 10.3 The most common upgrade route is to install it on the same machine
MySQL 8.0 If you already have a MySQL server at home
PostgreSQL 12 People who prefer PostgreSQL

On Home Assistant OS, install the MariaDB App from the Home Assistant repository under Settings → Apps. Home Assistant 2026.2 renamed Add-ons to Apps, so older instructions may say “Add-on store.” Apps are available only on Home Assistant OS. After installation, add this to configuration.yaml:

recorder:
  db_url: mysql://homeassistant:YOUR_PASSWORD@core-mariadb/homeassistant?charset=utf8mb4
  purge_keep_days: 14

core-mariadb is the App’s hostname on the internal network. The username, password, and database name must match the App configuration. For a database on another host, use the documented URL format:

mysql://user:password@SERVER_IP/DB_NAME?charset=utf8mb4
postgresql://user:password@SERVER_IP/DB_NAME
Warning: A database password written directly in configuration.yaml is plain text and is included in a full backup. Store the URL in secrets.yaml as mariadb_url: mysql://homeassistant:YOUR_PASSWORD@core-mariadb/homeassistant?charset=utf8mb4, then use db_url: !secret mariadb_url in the configuration. secrets.yaml is also sensitive and included in backups; this prevents accidental disclosure when sharing configuration snippets, not disclosure from a leaked backup.
Concept: MariaDB can improve write and query performance for larger datasets, but it does not change retention automatically. purge_keep_days still controls detailed history. For several years of high-resolution time-series data, consider the InfluxDB approach in the next section.

Advanced 2: InfluxDB and Grafana for long-term data

This architecture separates control, time-series storage, and visualization:

role Responsible for what Metaphor
Home Assistant Control your home and generate data command center
InfluxDB Stores time-series data for long-term analysis Warehouse
Grafana Visualizes stored data in dashboards Showroom

The official InfluxDB integration writes an additional copy of selected state data to InfluxDB. Local Recorder continues to run independently. You can therefore keep 7 days of detailed Recorder history while applying a separate 3-year policy in InfluxDB.

Key points in setting:

  • InfluxDB 1.x uses the combination of URL, account password, and database name, and authentication is optional (not enabled by default).
  • InfluxDB 2.x and 3.x use an organization, bucket, and access token. Authentication is required, and api_version: 2 selects the newer API. The integration documentation covers 1.x, 2.x, and 3.x.
  • For every version, configure filters. The integration supports include/exclude rules for domains, entities, and entity_globs. Sending every entity to InfluxDB merely moves uncontrolled growth to another database.
Warning: InfluxDB configuration and query languages differ substantially between major versions. Many online examples target older releases. Confirm your installed version, then follow the matching parameters in the current Home Assistant integration documentation.

InfluxDB and Grafana are available as community-maintained Apps from the hassio-addons Home Assistant Community Apps repository; they are not official Home Assistant Apps. Add that repository before installation as described in Chapter 20 and Appendix A. Apps are available only on Home Assistant OS; Container and Core installations require separate InfluxDB and Grafana deployments.

Tip: This route requires configuring three separate applications. If you just want to see last year's electricity usage, the built-in long-term statistics plus energy dashboard will suffice. The situations where InfluxDB is really needed are usually: you want to make very customized charts, you want to mix them with non-Home Assistant data sources, or you want to retain high-resolution raw data for several years.

Advanced 3: Use SQL integration to turn queries into sensors

SQL integration allows you to write a SQL query and turn the result into an entity, which can then be placed on a dashboard and used to trigger automation. Home Assistant documentation states that it can be added through the configuration process (UI) or written in YAML.

There is only one most classic use: Make the database size a sensor and display it directly on the dashboard.

  1. Settings → Devices & Services → Add integration

    Select the button in the lower-right corner and search for SQL.

  2. Database URL left blank

    db_url is optional. Leave it blank to query the database currently used by Recorder.

  3. Paste the query statement

    Home Assistant example given by the SQLite version is this sentence:

    SELECT ROUND(page_count * page_size / 1024 / 1024, 1) as size
FROM pragma_page_count(), pragma_page_size();

  4. Fill in the field size

    Enter size, matching as size in the query. The query must return a single result column.

  5. Set name and unit

    The name can be "database size", and the unit of the result is MiB. Home Assistant mentioned that you can set the device type to Data size and let the interface automatically convert units for you.

Add the resulting sensor to a dashboard as described in Chapter 6. You can also notify yourself when it exceeds a chosen threshold; see Chapter 7.

alias: Notify me if the database is too big
triggers:
  - trigger: numeric_state
    entity_id: sensor.database_size
    above: 2000
    for: "01:00:00"
conditions: []
actions:
  - action: notify.persistent_notification
    data:
      title: Database warning
      message: The database has exceeded 2000 MiB (approximately 2 GB), it's time to find out who is spamming it.
mode: single

notify.persistent_notification creates a persistent notification in the Home Assistant interface and requires no prior setup, making it suitable for testing. To notify a phone, use the action configured in Chapter 7. for: "01:00:00" requires the value to remain above the threshold for one hour, reducing alerts caused by brief fluctuations.

Warning: The query above is specific to SQLite. Do not use it with MariaDB or PostgreSQL; consult the documentation for an equivalent query in your database engine.
Danger: SQL integration sends queries directly to the database. Use read-only SELECT queries. Never enter DELETE, UPDATE, or DROP. Delete Recorder data only through recorder.purge or recorder.purge_entities.

Common problems

  1. Home Assistant responds very slowly

    Check Settings → System → Storage for free space, then view the estimated database size in Repairs. If the database is several GB, identify high-frequency sources, add appropriate exclude rules, restart, then run recorder.purge with repack: true and apply_filter: true. Confirm adequate free space before repacking.

  2. The memory card is broken and the system cannot be started.

    Recorder writes at each commit_interval, and sustained database growth places a heavy write load on consumer microSD cards. There is no universal lifespan figure. Reduce unnecessary writes by increasing commit_interval cautiously and excluding noisy entities; for long-term reliability, migrate the installation to suitable SSD or high-endurance storage.

  3. After rebooting, all the history is gone.

    Check the logs. A damaged database may have been moved aside while Home Assistant created a new one; database errors will identify this case. Alternatively, you may have switched from SQLite to MariaDB. Existing-history migration is not officially supported, so a new database begins empty by design.

  4. An entity cannot be found in history at all

    Check whether an exclude rule removed it or an include rule omitted it. Then confirm that the entity is enabled as described in Chapter 11. If it appears in History but not Activity, that can be normal because Activity omits sensors with units by default.

  5. The cleanup is finished, but the hard disk space has not increased.

    This is normal. Purging rows does not immediately return space to the operating system. repack rewrites the database to reclaim that space. The default auto_repack runs every second Sunday; if space is urgently needed and sufficient working space is available, run a purge with repack: true.

  6. An extreme value flattened the Energy chart

    Open Settings → Tools → Statistics, locate the entity and timestamp, and correct the invalid value. Make a backup first and follow the detailed procedure in this chapter’s Tools → Statistics section.

  7. The downloaded CSV is garbled when opened.

    Do not open directly by double-clicking. In Excel, use "Data → From Text/CSV" to import, and select UTF-8 for encoding; in Google Spreadsheet, use "File → Import", which usually automatically determines the correctness.

  8. The recorder action cannot be found, or there is no response after pressing it.

    First make sure you are on the right track: now Settings → Tools → Actions, not the "Developer Tools" on the sidebar (that location no longer exists after 2026.2). Furthermore, the actions of the recorder require administrator privileges to be executed. When logging in with a standard user account, the entire setting area cannot be entered. Switch back to the administrator account and try again.

FAQ

By changing purge_keep_days to 365, will all history be saved permanently?
It is technically possible but usually impractical. Retaining 365 days instead of 10 can produce roughly 36 times as much detailed-state history, slowing queries, enlarging backups, and increasing storage writes.

Use long-term statistics for eligible numeric data, and send selected high-resolution data to a dedicated time-series database when required. Set purge_keep_days according to how much detailed recent history you actually need; the source recommends 7 to 14 days for most installations.
Why does my temperature curve three months ago look smooth and different from what I saw then?
The older portion no longer uses full-resolution state history. Within the detailed retention window, History reads Recorder states; beyond it, eligible sensors use hourly long-term statistics. Brief spikes are averaged out, producing a smoother curve.

This is an intentional storage trade-off. If you require minute-level data after the Recorder retention period, configure suitable external time-series storage before that data is generated.
I added an entity to exclude, why is the old data still there?
Because the filtering rules only care about "whether you want to write from now on" and will not go back and delete things. There are two ways to clear existing old data:

One is execution recorder.purge and put apply_filter Set to true, it will apply the filtering rules in the profile to the old data. The second is to use recorder.purge_entities Just name that one entity_id, its keep_days The default is 0, which means that all data that meets the conditions will be deleted immediately.

Please note that after changing the profile, you must restart Home Assistant first for the new filtering rules to take effect.apply_filter Only then can the correct rules be applied.
After switching to MariaDB, will the previous history be transferred with it?
No. Home Assistant warns that changing Recorder databases can make existing history unavailable, and database migration is not officially supported. Unofficial migration scripts are unsupported and can damage data.

Switch early if you intend to change databases. Before changing a mature installation, export important History data to CSV and preserve a tested backup. Treat the new database as a new history baseline.
I just want to pour the data from a certain sensor into Excel to do my homework. What is the fastest way?
"History" in the sidebar → select the entity → set the time range → "Download data" in the upper right corner → get the CSV. The entire process does not require installing anything or writing any programs.

Two small reminders: Don’t expand the range too much at once. Use a day to test how long the file is before making a decision; also remember that what you get beyond 10 days will be the hourly average, not the original tick-by-tick data. If you want to make "detailed changes within a day", choose the last few days. If you want to make "long-term trend", just stretch it. Anyway, what you get is the summary value.
The backup files are getting bigger and bigger. Is it because of the database? Can I back up only the settings but not the history?
Yes, the database file is in the settings folder, and a full backup will include it. Home Assistant advice on backups on the "Clear Space" page is: set rules for how many copies to keep to prevent backups from accumulating, and try to save backups in a place other than Home Assistant.

The built-in backup interface allows you to choose whether to include media, shared folders and other items. However, the status of the "Exclude databases individually" option is different in different versions. Please refer to the actual check box that appears on your screen.

With or without that option, the most effective approach is the same: Let the database shrink first, and the backup will naturally be smaller. The sequence is to set exclude → reboot → run purge with repack → then create a backup.
Can "History" and "Activities" be removed from the sidebar? I can't use it.
Existing items on the sidebar can be individually hidden or reordered by long-pressing (on a phone) or pressing and holding on the sidebar to enter edit mode. This setting follows the user account. You can hide it without affecting other people at home. The operation details of different versions are slightly different, please refer to the prompts on your screen.

By the way, this editing mode can only organize "things already on the sidebar", and there is no way to pull the tools (Tools) moved into the settings in 2026.2 back to the sidebar - Home Assistant said that complete sidebar customization is still under planning.

But one thing to note: Hiding the sidebar items is just out of sight, but the data is still being recorded., how big or how big should the database be? If you want to save space, you have to rely on exclude and purge in this chapter. Hiding the sidebar does not help at all. And when something really happens and you need to find out "who opened the door last night", you will miss them very much.
How do I know which entity is flooding the database?
The most intuitive way to judge: Go to the history page and see who has the densest curves one by one. High update frequency and continuous changes in values must be the main suspect. Usually, these categories cannot be escaped - the power and position returned by the mobile app, the power/current socket reported second by second, the sun azimuth angle, and the network speed test.

If you want more accurate figures, the community has various SQL queries that directly count the number of entities in the database, which can be run with the SQL integration in this chapter. However, those query writing methods will become invalid as the database structure is adjusted. The old syntax found on the Internet may not still be usable. If you are not sure, you will fall back to the crude but always effective method of "seeing who has the densest curves."
