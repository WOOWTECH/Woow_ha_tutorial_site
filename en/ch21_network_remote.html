Chapter 21

Networking and remote access

Make Home Assistant reliable on your local network before exposing it remotely. Configure a stable address, compare four secure remote-access paths, and apply the security rules that must not be skipped.

Why is remote connection the easiest thing to do wrong?

Appendix A Having compared the four remote routes side by side, that article is “Which one to choose?” This chapter is "After making a choice, how to actually do it and what will happen if you do it wrong."

Network configuration has higher stakes than the earlier topics. A failed automation may leave a light off; an unsafe remote-access configuration can expose your home system to the internet.

Home Assistant may reveal occupancy by room, door and window states, camera images, lock controls, and arrival or departure times. Treat that access like a house key. The chapter therefore follows a deliberate order: stabilize the local network before configuring remote access.

After this chapter, you can:

  • Pin the IP of the Home Assistant host on the router so it never runs away
  • Understand homeassistant.local Why sometimes it works and sometimes it doesn't, and you know what to do when it doesn't work.
  • Choose one of the four external routes and follow the steps to complete it
  • Do you know why you cannot log in if you do not set the two lines after the reverse proxy?
  • know what things never do, including the "Open 8123 port forward" tutorial that you will definitely see on the Internet.
Warning: Home Assistant 2026.8 version changes network-related settings Move the entire UI into , originally written in configuration.yaml of http: The block has entered the elimination period. This chapter will focus on the new UI location and the old YAML writing method as a supplement. If your version is older than 2026.8, the screen you see will be different. This is noted in each paragraph below.

Basics of local network: IP, DHCP, and why they must be fixed

It is fastest to think of it in terms of “building public IP address”.

Your router assigns an address to every device on the local network, including phones, computers, televisions, and the Home Assistant host. An address such as 192.168.1.37 is an IP address.

DHCP assigns these local addresses automatically. This is convenient, but the addresses are leases: a device may receive a different address later.

The lease will expire. Your Home Assistant host is today 192.168.1.37, restart after a power trip, the administrator may send it 192.168.1.52, while .37 You were given a new sweeping robot.

What will be damaged if the address is lost?

Somefeature that will breakSymptoms
URLs that you have bookmarked in your browserWhen you open it, it will spin in circles, and finally it will say "Unable to connect".

port forward rules on the routerThe rules also point to the old address, which is equivalent to pointing to someone else's house.

So the rules are simple: The IP of the Home Assistant host must be fixed. This is not an advanced technique, this is step zero that must be done.

Find the MAC address

To make a reservation on the router, you must first let the router recognize "which one is Home Assistant." The way to recognize it is MAC Address —A set of numbers that are engraved into each network card at the factory. They look like DC:A6:32:1B:4E:F0.

The IP address can change, but the MAC address remains stable. A DHCP reservation tells the router: “When the device with this MAC address requests a lease, assign 192.168.1.37.”

Do it yourself: Pin the host IP and confirm the network page

  1. Find out the host’s IP and MAC in Home Assistant

    go to Settings → System → Network. This page will list your host's network interface (wired, wireless) and the IP address it currently has. Copy the IP.

    The MAC address may not be displayed on this page. The best place to look is in the router's list of connected devices. —Open the router management page and look for the name containing homeassistant, or the one whose IP is the same as the one you just copied down, the MAC will be listed next to it. This also has another advantage: if you want to make a reservation later, you have to do it on the router, and You already there.

  2. Log in to the router management page

    The router's management URL is usually 192.168.1.1 or 192.168.0.1, is also often printed on a sticker under the host. The password is also on the sticker - if you have never changed the default password, Change it now, which is the foundation for all subsequent security measures.

  3. Find the DHCP reserved settings page

    Every router has a different name, and this is the trickiest step. Common names include: DHCP reserved address, DHCP Reservation, Address Reservation, Static DHCP, Static Lease, fixed allocation. The location is usually under "Local Area Network/LAN" or "Advanced Settings → DHCP Server".

    If you can't find it, use your router model to search for "Model + DHCP Reserved". This feature is available even on basic home routers, but it is just hidden deep inside.

  4. Add a new reservation

    Fill in the MAC address copied in step 1 and specify the IP you want to give. It is recommended to choose a number that is easy to remember and difficult to bump into, for example 192.168.1.10. Write "Home Assistant" in the remarks column, and you will thank you now three months later.

    Archive. Some routers need to be restarted to take effect.

  5. Let the host get the number again

    After the reservation is set, the host will not be changed immediately until the old lease expires. The fastest way is to restart the Home Assistant host (Settings → System Power menu in the upper-right corner → Restart system), or unplug the network cable.

  6. Acceptance

    After reopening, Return to Settings → System → Network, confirm that the IP displayed is the one you specified. Then use the new IP to open the webpage, and you can log in normally and it will be successful. Bookmark this URL instead of your original one.

  7. Fill in the internal URL

    Also in Settings → System → Network This page has two spaces: "Internal URL" and "External URL". Fill in the internal URL with the one you just pinned, for example http://192.168.1.10:8123.

    These two grids Just fill in the connection port and do not add the path later.. fill in http://192.168.1.10:8123/lovelace This way of writing will cause the subsequent link generation function to receive a strange URL, which is a common cause of trouble.

Concept: Why are these two boxes important? Because Home Assistant uses these two boxes when it generates notification links, pushes camera images to the phone, or tells the app "where you should go." If you fill it in incorrectly, the symptoms will be very strange: all the functions are there, but you cannot access the notification when you click on it.

What is homeassistant.local and the number 8123?

How .local addresses use mDNS

During installation, you may have opened homeassistant.local:8123 without configuring a local DNS server. mDNS is what resolves that name.

mDNS (Multicast DNS) asks every device on the local network whether it owns a requested name:

  1. Your computer broadcasts to the entire local network

    "Is there anyone called HomeAssistant?" This sentence is sent out in a multicast manner, and every host in the same network segment can hear it.

  2. Home Assistant responds

    "I am, I'm at 192.168.1.10."

  3. The client caches the result and connects

    The exchange does not require a central DNS server. Apple calls its implementation Bonjour, while Linux commonly uses Avahi.

Why it often fails

Several network settings can block this multicast exchange:

Failure reasonHow to judgeSolution
You and the host are not on the same network segment (VLAN or guest network)The phone can be connected to the main Wi-Fi, but not the guest Wi-Fi.Use IP direct connection, or enable mDNS forwarding on the router
A router or switch is blocking multicast trafficThe whole family cannot connect to .local, but the direct IP connection is normalFind the settings for IGMP Snooping, Multicast, and mDNS in the router, or directly switch to IP
The device's Wi-Fi has "Client Isolation" turned onThe phone can connect to the internet, but cannot connect to any host at home.Turn off the router’s AP Isolation / Client Isolation
The operating system or browser does not support itSome Android versions, some enterprise network environmentsUse IP
You are outsideIt will definitely be inaccessible if you leave homemDNS Originally only valid in the local network, this is not broken
There are two devices on the Internet called homeassistant.Even in the past it was another hostRename one of them
Warning: The most important sentence— homeassistant.local It will never work on the internet. It is not your public URL and cannot be used to set up port forward. I saw someone asking "You cannot connect to homeassistant.local when I call it outside." The answer is this.

Port 8123 and the 2026.8 change

If the IP is a address, The port is the service number behind the address.. The same host can run many services at the same time, and the service number is used to distinguish who is who. The number that Home Assistant historically uses is 8123, so the URL must be written as http://192.168.1.10:8123.

But this matter has changed in version 2026.8, and the changes are worth knowing:

Your situationDefault portHow long is the URL?
Fresh Home Assistant OS installation after 2026.880http://homeassistant.local (no port number required)
The system that was running before 2026.8 was upgraded.maintain 8123http://homeassistant.local:8123
Container/Docker installation8123http://192.168.1.10:8123

Home Assistant documentation on the revision is very clear: Nothing will change on systems that are already running and you do not need to do anything. This only affects fresh installations of Home Assistant OS. In other words, most online tutorials :8123 It's probably right for you.

Why change? because 80 It is the default number of the page, and the browser will automatically fill it in, so the URL can be shortened - purely to reduce the threshold for beginners.

Tip: After 2026.8 you can Settings → System → Network Change the connection port. Home Assistant has put a rollback safeguard here: After making the changes, the system will wait for you to confirm "Is it still connected?" If you don't confirm within five minutes, it will treat it as something wrong and automatically put back the old settings and restart. So even if you enter an unreachable configuration, you won't lock yourself out.

  • Do not want to bother, want to use Alexa or Google Voice, and want to support official development → Nabu Casa. This is also the option that Home Assistant documentation itself labels as "the simplest and Low exposure for most people."

Route 1: Home Assistant Cloud (Nabu Casa)

This is an official subscription service operated by itself. The subscription fee goes directly back to support the development of items such as Home Assistant, ESPHome, and Z-Wave JS. Therefore, it is at the same time “the easiest solution” and “the most direct way to sponsor”.

What it provides

Your host actively establishes a connection with Nabu Casa's server, and all subsequent requests from the outside come in through this existing connection. There is no need to open inbound router ports —This is why it is not afraid of CGNAT or your IP changing every day.

Implementation steps

  1. Find cloud settings

    go to Settings → System → Network, under "Home Assistant URL" Internet In that column, turn on "Use Home Assistant Cloud". Another entrance is Settings → Home Assistant Cloud, both sides can go to the same place, whichever is on your screen.

  2. Register or log in to an account

    Register a Nabu Casa account with your email address. This account is separate from your local Home Assistant login. At registration, you can select “Start a one-month free trial” without paying in advance.

  3. Turn on the remote connection switch

    After logging in, turn on the remote control switch. The system will allocate a fixed set of URLs to you. The format is a long string of codes plus .ui.nabu.casa, for example https://abcd1234-ef56-7890-abcd-ef1234567890.ui.nabu.casa.

    The generated address is not memorable, but it is unique, uses HTTPS, and remains stable.

  4. Save the URL into the mobile app

    Open the Companion App (Chapter 7 The one that is installed), go to the App settings and fill this URL into the "External URL". The internal URL maintains your IP on the local network. The app will decide which one to use now.

  5. Test

    Turn off your phone's Wi-Fi, use only the mobile network, and open the app. If you can get in, you will be successful.

Warning: Home Assistant document has an easy-to-follow explanation: For connections coming through Home Assistant Cloud, all IP addresses from the system’s perspective are 127.0.0.1. This means that the "IP Blocking" function to be discussed later has little ability to identify cloud connections - blocking one is equivalent to blocking all cloud users. This is why people who use Nabu Casa Rely on MFA more than IP blocking.
Tip: If you have your own domain, official support is to change the default URL to home.yourdomain.com This kind of custom URL. This function requires Home Assistant 2023.9.0 or above. The setting method is to add it in the Nabu Casa account and add a corresponding record to your DNS service provider.

The concept is exactly the same as Nabu Casa— Your host actively connects to the outside without opening any ports. —The difference is that it is operated by Cloudflare and uses your own domain, so the URL can be very beautiful.

Implementation steps

  1. Give the domain to Cloudflare first

    Add your domain in the Cloudflare dashboard and it will give you two sets of name servers. Go back to where you bought the domain and change the name servers to the two groups provided by Cloudflare. You have to wait for this step to take effect, sometimes a few minutes and sometimes a few hours.

  2. Add the third-party add-on repository

    Cloudflared is not built in, so add its repository. Go to Settings → Apps (called Add-ons in older versions) → Install app → upper-right three-dot menu → Repositories. Paste https://github.com/homeassistant-apps/repository, then select Add.

    Older tutorials may use brenner-tobias/addon-cloudflared. That repository states that it moved to the homeassistant-apps organization, so use the current URL above. Chapter 20 covers the complete repository process.

  3. Install and set up Cloudflared

    After the repository is added, a new card will appear in the list. Find Cloudflared in it and install it. Go to its settings page and fill in the external URL you want to use, for example ha.yourdomain.com.

  4. Start and complete authorization

    Launch the app and then Go to its log page. It will print out an authorization URL, which you need to open with a browser, log in to Cloudflare, and authorize this channel to connect to your domain. This step is most likely to be missed by beginners - they don't know what to do without looking at the log.

  5. Set up trusted proxy

    The traffic on this path is transferred from the App container to Home Assistant, which is equivalent to an extra layer of proxy in the middle. Without setting a trust proxy, the request will be directly blocked by Home Assistant. (Typical symptoms are that the page can be opened but cannot be logged in, or the entire page 400 Bad Request), please refer to the section "Reverse proxy must be set up" below for the setting method.

  6. Test

    Turn off your phone's Wi-Fi and turn it on using your mobile network https://ha.yourdomain.com.

Tip: The Cloudflare dashboard can add another layer of access control, requiring verification before accessing the Home Assistant login page. For people who say "I don't want my login page to be scanned by the whole world", this is the biggest plus point of this path.

Route 3: VPN (Tailscale or WireGuard)

The first two paths are to "put Home Assistant securely on the Internet." VPN is a completely different idea: Connect your phone to your home network.

The metaphor of a key is the most vivid: the first two are to install a very strict guard at the door, but the VPN has no door at all, and only the person who gets the key knows that the house exists. Because Home Assistant has never been open to the public internet from beginning to end, This is the strongest security path among the four..

Tailscale: the simplest VPN option

Tailscale helps you automate all the hardest parts of VPN (key exchange, NAT traversal, and path finding). It can even pass through CGNAT, which is important for users behind carrier-grade NAT in any region.

  1. Register for a Tailscale account

    Just log in with a Google or GitHub account, and the free quota for personal use is more than enough for family scenes.

  2. Join the community app repository

    Go to Settings → Apps → Install app → upper-right three-dot menu → Repositories, then add https://github.com/hassio-addons/repository. This Home Assistant Community Add-ons repository includes Tailscale and WireGuard.

  3. Install and start Tailscale

    Start after installation, and then View log tab, there will be an authorization URL inside. Open it with a browser and add the host to your Tailscale network.

  4. Tailscale is also installed on phones

    Install the Tailscale App from the App Store or Play Store and log in with the same account.

  5. Connect with Tailscale URL

    After connecting to the VPN, you can use Home Assistant to connect to an address on the Tailscale network. If MagicDNS is turned on, the URL will look like homeassistant.tail1234.ts.net This format (tail1234 It is assigned to you by the system).

Concept: Tailscale App has one called advertise_routes The default setting is to share your home's local network segment. The advantage of turning it on is: after connecting to the VPN, you can not only connect to Home Assistant, but also the NAS, printer, and router management pages at home, which means that your phone can reach that local subnet. Very useful during maintenance.
Warning: If you use Tailscale's Serve or Funnel function to share externally, the traffic will pass through a layer of local proxy. Also set up a trusted proxy, and the trusted address is 127.0.0.1. If you don't set it, you will keep being asked to log in but unable to log in. Simply using VPN direct connection (without turning on Serve/Funnel) does not require this step.

WireGuard is the same technology used at the bottom of Tailscale. The difference is that you build it yourself and manage the keys yourself. Community Add-ons repository (the one above hassio-addons/repository), WireGuard can be installed.

Warning: The VPN path has inherent limitations— Cloud voice assistants such as Alexa and Google Assistant cannot be used. Because their servers are on the Internet, not in your VPN, they will never be able to connect to your Home Assistant. If you want the voice, you have to match Nabu Casa, or use the local voice (Chapter 19).

Implementation steps (taking the shortest path of Duck DNS as an example)

  1. First make sure you are not under CGNAT

    Do this step first, otherwise all the rest will be wasted. Method: Log in to the router, find the WAN status page, and see the public IP it displays. Then use your phone or computer to search for "My IP" to see the IP seen by the internet.

    If the addresses match, this path can work. If they differ, you are likely behind CGNAT and this path will fail. Choose one of the first three options instead.

    Another way to judge: If the router WAN IP falls 100.64.x.x Arrive 100.127.x.x This range is a section specifically used by internet service provider operators for CGNAT and can be determined directly.

  2. Register Duck DNS

    Go to the Duck DNS website to log in with a social account, apply for a subdomain, and change the string at the top of the page token Copy it.

  3. Install and set up Duck DNS App

    Install Duck DNS from Home Assistant App Store. Fill in the settings page token and domains(the domain you applied for), and then change the accept_terms Change to true —Home Assistant document writes very clearly: "Change the value to true to use the Let's Encrypt service."

    The default certificate file name is fullchain.pem and privkey.pem, do not change it without any special reason.

    This app takes the certificate DNS-01 Verification — In plain words, "Let's Encrypt will not connect to your home, it will check the DNS record of your domain to confirm that the domain is yours." So Just to get the credentials, you do not need to make any holes in the router. Home Assistant document also reminds that if you connect the Duck DNS domain to your own domain, remember to add a CNAME to the name used for verification, otherwise DNS-01 cannot be found and it will fail.

  4. Install NGINX SSL proxy

    Install Home Assistant NGINX Home Assistant SSL proxy. Set page filling domain(your Duck DNS URL),certfile and keyfile(These are the two file names above, they will be placed in /ssl folder).

  5. Set up trusted proxy

    If you do not do this step, you will definitely fail in the next step. See next section.

  6. Forward port 443 on the router

    This step is where you really need to make the hole: Only forward 443 (HTTPS) to your host, with the destination IP being the one you nailed in the first section of this chapter.

    Do not open any one except 443. —especially 8123 Never transfer (That is equivalent to hanging the unencrypted login page directly on the Internet. See the next section for the reason). There is no need to transfer port 80. NGINX App's port 80 is turned off by default, and your credentials are obtained through DNS verification, not port 80.

  7. Fill in the external URL and test

    Go to Settings → System → Network, fill in the external URL https://yourdomain.duckdns.org. Then turn off the phone Wi-Fi test.

Danger: The only part of this road that requires a hole in the router is 443. After opening it, your login page is on the Internet, and scanning robots around the world will find it in minutes. So those who take this path, The section on "Information Security Hard Rules" that follows is required reading, not optional reading..

Behind the reverse proxy, you will not be able to log in if you do not set these two settings.

This section is the most frequently asked help question in the entire chapter. As long as you use Cloudflare Tunnel, NGINX, Tailscale Serve/Funnel, or any form of reverse proxy, Will encounter.

Why it breaks: Home Assistant sees the proxy, not you

Under normal circumstances, when Home Assistant receives a request, it will look at "Which IP this request came from" to record the login, determine whether it is an intranet, and perform IP blocking.

But after inserting a reverse proxy in the middle, all requests will appear in the eyes of Home Assistant. They all come from the proxy's host.. You are in one city and a family member is in another, and there is a internet scanner - they all look exactly the same.

The solution is that the proxy will attach a note to the request saying X-Forwarded-For, it says "The real source of this request is xxx". But Home Assistant Default is not to trust this note, because anyone can forge it - if you believe it casually, an attacker can just forge a note that says "I am 127.0.0.1" and install to be this host.

So you have to explicitly tell Home Assistant two things: (1) Please trust this note; (2) Only notes from these IPs count.

Danger: Official documentation describe the incident as " If these options are not set, requests from the reverse proxy will be blocked”, and this is a deliberate design behavior, not a bug. The description of NGINX App is more specific: "Requests received through this proxy 400 Bad Request, then you probably missed it trusted_proxies settings. "The symptoms are usually being able to open a webpage, entering the account password but not being able to enter, or simply getting a 400."

Hard rules for security: these things are non-negotiable

Home Assistant safety checklist actually only lists three core principles: "Use a strong, unique password for each account and turn on multi-factor authentication.", "Put sensitive data in secrets (remember to back up)", "Follow monthly version updates". Here are the actions you should take to put them into Method today.

Warning: There is a point in Article 2 that many people have misunderstood, and Home Assistant specifically noted: put password in secrets.yaml It will not be encrypted. That's just for "centralized management so that you can share your profile without leaking it," not a safe. Therefore, the backup files should be treated as confidential, and do not throw away the public folder of the cloud drive (see the backup processing Chapter 9).

Rule 1: Do not port forward 8123 directly to the public internet

Danger: The most common tutorial on the Internet - "Add a rule to the router to transfer 8123, and you can connect from the outside" - is the only Method explicitly prohibited in this chapter. There are three reasons, each of which is fatal:
(1) The default is http:// Without encryption, your account password is The plain text of streaking, any intermediate node can be seen.
(2) Scanning robots scan 8123 all over the world all day long. You will be found within a few minutes of driving, and then there will be non-stop brute force cracking.
(3) Once Home Assistant is compromised, it means that all your door locks, cameras, and records of whether you are home or not are handed over.

If you have already opened it, Now go to the router and delete that rule., and then choose one of the first four paths to redo. This is no exaggeration, this is the most important sentence in this chapter.

Rule 2: Be sure to open an MFA

Multi-factor authentication (MFA / two-step verification) means that it is not enough to have a password, but also to enter a six-digit number that changes every 30 seconds on your phone. If the password is leaked, the attacker still can't get in without your phone.

  1. Open the secure tab of your profile page

    Click your name in the lower-left corner to enter User profile, switch to Security Tab.

  2. Enable multi-factor authentication module

    Find the area "Multi-factor authentication modules" and click Enable.

  3. Scan the QR Code using the validator app

    First install a validator app on your phone, scan the QR Code on the screen, and then fill in the six-digit number displayed by the app to confirm.

  4. Keep the backup code

    backup information given to you during the setup process Must be stored somewhere other than your phone. If your phone is dropped and there is no backup, you will be locked out of your home.

  5. Do this once for every account in the family

    It is useless if you open it yourself. Your family member’s account password is 123456 It's the same breach. Chapter 5 There are complete instructions for multi-user management.

Tip: In addition to the authenticator app, Home Assistant also has a notification-based authentication module that will send the one-time password to the place you specify through notifications. But official documentation warn of its weaknesses: This module has no way of knowing whether the notification was successfully delivered. If you don't receive the notification, you won't be able to log in. Therefore, the main force is to use the authenticator app which is more stable.

Rule 3: Turn on IP blocking

Home Assistant has a built-in function: If the same IP fails to log in for a certain number of times, it will be blocked.. This is the most effective way to deal with brute force cracking.

Set location at Settings → System → Network, two fields:

Official field nameFunctionRecommended value

(IP blocking enabled)		Turn on auto-blockingturn on

(Number of login attempts before being blocked)		Official description: "The number of failed logins allowed before the IP address is blocked. Set to -1 Automatic blocking can be deactivated. "5 or so. If it's too low, you'll be locked out if you make a typo yourself.

Home Assistant writes each blocked address to ip_bans.yaml together with the UTC time when it was added. To remove a ban, delete the corresponding entry and restart Home Assistant.

Warning: Two common failure scenes.
(1) When using Home Assistant Cloud, Home Assistant stated that all cloud connections appear to be 127.0.0.1, so IP blocking is basically ineffective against them, and your line of defense depends on MFA.
(2) If the reverse proxy does not set up a trusted proxy, all requests will appear to come from the proxy. Blocking one is equivalent to blocking all - you will also lock yourself out. This is back to the previous section. First, let us trusted_proxies configure it correctly.

Rule 4: Only open necessary external services

Take inventory of how many inbound ports are open on your router. Many people's rules were opened several years ago just to watch the monitor, download something, or play a certain game, and they have long forgotten it.

Site level: VLAN, guest network, multi-layer NAT

What I talked about before was “one home, one router”. If you are dealing with an office, a store, or a more elegant residence, there will be three more questions.

Put IoT devices into separate network segments

The problem lies with cheap smart sockets, light bulbs, and camera bodies: their firmware quality varies, and some are never updated after using them. A compromised smart socket, if it is on the same network segment as your laptop or NAS, is a ready springboard.

The solution is VLAN (Virtual Area Network): Cut out several mutually isolated logical networks on the same set of physical wires. A common cutting method:

Network segmentWhat to putWho can be reached?
Main network segmentComputer, phone, NAS, Home Assistant hostCan connect to all network segments
IoT network segmentSockets, light bulbs, sensors, TVsYou can only connect to the internet and cannot actively connect to the main network segment.
Camera segmentIP Cam, NVRmost stringent, usually Even external networks are prohibited, only allows Home Assistant to capture the screen
Guest segmentGuest's phoneI can only access the Internet and cannot see anything in your home.
Warning: After switching to VLAN, you will almost certainly encounter Device automatic exploration all failed. Because Home Assistant relies on mDNS "shout" to find new devices, and the shout will not cross network segments by default. You need to additionally enable mDNS forwarding on the router or firewall (different brands have different names, common ones include mDNS Repeater, Avahi Reflector, Bonjour Gateway), and open the necessary one-way rules to allow Home Assistant to actively connect to the IoT network segment. Cutting VLAN without dealing with this matter is the most common reason for overturning the case.
Tip: If your router only has a "guest network" switch and does not have full VLAN functionality, it is a simplified version of two-segment isolation - throw the least trusted devices and guests into the guest network, and leave the main network segment for serious devices. It's rough, but much better than all mixed together, and it can be done this afternoon.

Multi-layer NAT: Two routers at home

A very common situation: the modem provided by the internet service provider is itself a router. You think it has poor Wi-Fi, so you connect it yourself. The result is a two-layer NAT, and your Home Assistant host is actually hiding behind two doors.

How to judge: Log in to your own router and look at the WAN IP. if it shows 192.168.x.x or 10.x.x.x With this kind of private address, you're under multiple layers of NAT.

SolutionMethodEvaluation
Change the internet service provider's host to bridge modeCall internet service provider customer service and ask them to change it, or set it yourself on the modem management page.Cleanest. From now on there is only one layer of NAT
Both floors are equipped with port forwardThe outer layer forwards it to the inner layer router, and the inner layer forwards it to the host.Active but fragile, if you reset any level, you will have to start over again.
Switch to a solution that does not require port forwardNabu Casa, Cloudflare Tunnel, TailscaleThe most trouble-free. Multi-layer NAT is no problem for them

See the third column? This is why this chapter pushes those three paths all the way - They bypass the three most annoying problems of CGNAT, multi-layer NAT, and changing public IP at once.

Pre-delivery checklist

  • The host IP has been reserved on the router and recorded in the handover file
  • The router management password has been changed and is not the factory default.
  • The internal URL and external URL have been filled in and tested
  • MFA is turned on for all accounts and IP blocking is enabled
  • There is no rule on the router pointing to 8123
  • UPnP and router remote management are closed
  • The backup is scheduled and saved to a location other than the host (Chapter 9)
  • If there is a VLAN: mDNS forwarding has been configured and new device discovery has been tested
  • The expiration and renewal mechanism of the certificate has been confirmed to be automatically executed.

Troubleshooting

  1. Certificate application failed, Let's Encrypt keeps reporting errors

    Let us figure one thing out first: Duck DNS App uses DNS-01 verification, Let's Encrypt checks the DNS records of your domain and will not connect to your home. So "You cannot get the certificate" Usually it has nothing to do with port, do not rush to open ports on the router.

    Check in this order. (1) Are the DNS settings correct?:Duck DNS has the domain over there really been built, has the token been posted incorrectly, and if you have connected your own domain, has the CNAME used for verification been added? (2) Is DNS effective?: It will take some time for the newly modified record to be visible to the entire network. If you press it too early, it will fail. (3) Have you accepted the terms?: In Duck DNS App accept_terms Forgot to change to true It's a common error. (4) Is the current flow restricted?: Let's Encrypt has an upper limit on the number of applications for the same domain within a short period of time. If you try again and again, you will be locked for a period of time - the only solution at this time is stop and wait, continuing to press will only make things worse. (5) View the App’s log files, the real reasons for the error are written there, do not just read the red letters.

  2. You can connect at home, but you cannot connect when you go out (or vice versa)

    Almost all are problems with the internal and internet URL settings. Go to Settings → System → Network Confirm internal and external URLs Both boxes are filled in, and both are filled in correctly.. Then open the settings of the Companion App on your phone and confirm that the App also has these two URLs.

    Special reminder: these two spaces Stop filling in the connection port and do not continue to follow the path.. Fill in .../lovelace This will cause notification links and camera push notifications to lead to strange URLs, and the symptoms are all kinds of strange and difficult to associate here.

    Another situation is that "it works fine when I go out, but not when I go home." Usually the IP written in the internal URL has expired - go back to the first section of this chapter to nail the IP.

  3. The page can be opened, but after entering the account password, it cannot be entered, or it will get 400

    This is a typical symptom of the reverse proxy not having a trusted proxy. Return to the section "Reverse proxy must be set up" and set Trust X-Forwarded-For open, Trusted proxies Fill in the correct address (App-based proxies are 172.30.33.0/24, Tailscale Serve/Funnel is 127.0.0.1), save and restart.

    If it still doesn't work if you have set it up, check whether it is set in the old configuration.yaml But the version has been upgraded to 2026.8 - at this time, it is time to refer to the UI value and delete the YAML block. If you cannot find the settings in the UI after deleting them, forcefully refresh the browser first.

  4. DDNS is set up, but still cannot be accessible remotely - CGNAT

    Compare the router’s WAN address with the result from an online “My IP” check. If they differ, you may be behind CGNAT, where an internet service provider allows many customers to share one public IP address.

    Behind CGNAT, DDNS and port forwarding cannot provide inbound access because you do not have your own public IP address. You can (1) ask your internet service provider whether a public IP is available, possibly for an additional fee or plan change; (2) use Nabu Casa, Cloudflare Tunnel, or Tailscale; or (3) omit remote access. For most households, option (2) is the practical choice.

  5. homeassistant.local suddenly stops working

    Make sure you are home first. Double check that the phone is not connected to guest Wi-Fi or another network segment. If everything is correct, use IP direct connection to verify that the host is still alive - if you can use IP to get in, it means it is just an mDNS problem, not that the host is down. The long-term solution is to peg the IP and use the IP as a bookmark instead, which will be the least likely to happen.

  6. Can't connect after changing the port

    If you changed the UI after 2026.8, Don't be nervous, don't do anything —Home Assistant design is to wait for your confirmation after the change is completed. If there is no confirmation within five minutes, the old settings will be automatically put back and restarted. Wait for the automatic rollback to complete.

    If it is an old version or the Container installation has been manually modified, you have to change it back from the host (connect the screen keyboard, or change the Docker port corresponding).

  7. Blocked by own IP block

    Entering the wrong password too many times triggered the block. The solution is to edit from the host side ip_bans.yaml, delete your own, and then restart Home Assistant. If you can't access the file, try another network (for example, turn on a mobile network hotspot on your phone), and your IP will change.

  8. New device cannot be found after switching VLAN

    Within expectations. Automatic discovery relies on multicast traffic that does not cross network segments. Go to the router or firewall to enable mDNS forwarding (mDNS Repeater / Avahi Reflector / Bonjour Gateway), and confirm that there are rules that allow Home Assistant to actively connect to the IoT network segment.

FAQ

You only want to check whether the lights at home are on outside. Do I really need to make it so complicated?
No. Home Assistant Cloud provides managed remote access without changing router settings, and the documentation describes it as the simplest secure option for most people. The other paths serve readers who prefer a self-managed option, want to learn networking, or have a more complex network. Consider whether the subscription costs less than the time you would spend configuring and maintaining an alternative; its revenue supports Home Assistant development.
The tutorials I saw on the Internet all said that just opening the 8123 port forward would be sufficient. Why do you say no?
Because most of those tutorials were very old, and the threat environment was different when they were written than it is now. Three specific reasons: no encryption (The default is http://, the account password is in clear text on the Internet), will be scanned (Scanning robots scan for 8123 all over the world all day long, and usually come to your door within a few minutes), The consequences are too serious (Home Assistant contains your door locks, cameras, and records of whether you are at home or not). All four paths described in this chapter achieve the same results and are much safer, so there is no reason to take that one.
My Home Assistant has been upgraded from 2026.8, do I need to add :8123 to the URL?
Yes. Home Assistant revision description made it very clear: Nothing will change on the system you're already running, and you don't need to do anything. The new presets only affect newly installed Home Assistant OS. So your original :8123 Just keep using it. If you really want to switch to a version that does not require dialing a number, you can get it after 2026.8 Settings → System → Network Change it yourself, and it will automatically recover within five minutes if it is changed. The risk is not high - but after the change, remember to update all bookmarks, app settings, and reverse proxy settings.
My configuration.yaml There is http: Block, do you want to delete it now?
Yes. from 2026.7.5 When the version starts, Home Assistant will pop up a warning saying that the HTTP YAML setting has been eliminated and the setting has been imported for you. Please import it for you. http: Block removed and noted "This will stop working in version 2027.2.0, please deal with it before upgrading". When upgrading, your original settings will be automatically imported into the UI. The correct method is: first come first Settings → System → Network Confirm that the settings are all in (trusted_proxies Pay special attention to whether they have been brought over correctly), and then take them after confirming that there is no problem configuration.yaml the whole inside http: Delete the block and restart. If you cannot find the setting on the UI after deleting it, force refresh the browser first.
Can Nabu Casa and Tailscale be opened at the same time?
Yes, and it's a very practical combination. Nabu Casa is for daily use by your family (you can use it by just posting the URL, and can also connect to voice assistants), and Tailscale is for you to maintain yourself (after connecting, you can access the entire home network, and you can open the router management page and NAS). The two do not interfere with each other. The only thing to note is that if Tailscale has Serve or Funnel enabled, remember to 127.0.0.1 Add to list of trusted proxies.
Why cannot I run Alexa or Google Voice on the VPN route?
Because the logic of VPN is to "pull your device into the home network", and the servers of Alexa and Google Assistant are on the Internet, they cannot join your VPN, so they will never be able to connect to your Home Assistant. If you want a cloud voice assistant, you have to go to Nabu Casa (this connection is included in the subscription), or switch to a voice solution that runs completely locally and does not require external connections (Chapter 19).
Trusted proxies I can be lazy and fill in 0.0.0.0/0 ? Anyway, no one in my family wants to be hacked.
No; this is the most non-negotiable aspect of this chapter.0.0.0.0/0 means "I trust the source IP claimed by anyone." The attacker only needs to forge a request X-Forwarded-For header, you can install to be any IP - your IP blocking is completely invalid, your login records are all fake, and you can't even trace it afterwards. And "no one wants to hack me" is an illusion. The scanning robot doesn't pick targets, it scans the entire Internet. The correct approach is to only fill in the proxy address that you really know: fill in the app-based proxy address 172.30.33.0/24, fill in Tailscale Serve/Funnel 127.0.0.1.
I'm not sure if I'm under CGNAT, how can I confirm it in thirty seconds?
Just compare the two numbers. first one: Log in to the router and find the public IP displayed on the WAN status page. second: Search "My IP" on your phone or computer to see the IP the website tells you. Both are the same It means you have a real public IP, DDNS is the way to go. Two different There is a layer of internet service provider operators between the representatives, and you are under CGNAT. Also, if the router WAN IP falls on 100.64.x.x Arrive 100.127.x.x This section is reserved exclusively for CGNAT by internet service provider operators and can be determined directly. Please use Nabu Casa, Cloudflare Tunnel or Tailscale under CGNAT, these three will not be affected at all.
Why do I enable IP blocking, but all attack records show 127.0.0.1?
There are two possibilities. First: with Home Assistant Cloud remote access, the documentation says all cloud connections appear as 127.0.0.1. IP blocking therefore has little effect on those connections; rely on MFA. Second: a reverse proxy is not configured as trusted, so every request appears to come from the proxy. Do not block that address, because you would block every user, including yourself. Configure trusted_proxies correctly.
After cutting VLANs to isolate IoT devices, can Home Assistant still find them?
It requires additional settings to find it. Automatic discovery relies on mDNS's "shout within the network segment" mechanism. By default, the shout will not cross VLANs, so you will find that all new devices cannot be discovered. The solution is to enable mDNS forwarding on the router or firewall (each name is different: mDNS Repeater, Avahi Reflector, Bonjour Gateway), and additionally allow the Home Assistant host One way Connect to the IoT network segment (the IoT side still cannot connect back to the main network segment). This is the most common cause of overturning at the scene. Before proceeding, make sure your network device supports these functions.
