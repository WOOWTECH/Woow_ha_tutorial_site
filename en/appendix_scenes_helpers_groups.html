Appendix B

Scenes, helpers, and groups

Scenes, helpers, and groups are built-in Home Assistant building blocks. Combine them to express useful automation logic without unnecessary templates or custom code.

Scenes: restore a defined state with one action

A scene is a "state snapshot" of a set of entities. When called, all entities instantly return to the state you set.

Terminology update: Home Assistant renamed “Service” to Action in 2024.8. YAML changed from service: to action: and from service_data: to data:. Since 2024.10, automation sections use the plural keys triggers:, conditions:, and actions:, and each trigger changed from platform: to trigger:. Starting in 2026.2, “Developer Tools” appears as Tools under Settings → Tools. This page uses the new terminology. Existing configurations using supported legacy keys do not need to be rewritten immediately.

Method 1: Record from the current state

  1. First manually adjust your home to how you want it

    For example: main light 40%, atmosphere light purple, air conditioner 26°C, curtains 30%, and Bluetooth on the speaker.

  2. Settings → Automations & Scenes → Scenes tab → + Add new scene

    Select "Create from current state" → select which entities to include → save. HA treats the current value as a scene snapshot.

  3. Name, for example: "Movie Mode" → Save

    Entity ID will be scene.movie_mode.

Method 2: Manually fill in the target value of each entity

Use this when you want a "holiday scene" but it's not convenient to really adjust it now (you can't disturb the neighbors in the middle of the night). Start from a blank scene, add entities one by one + fill in the target state.

Activate a scene

  • UI: Put a Button card on the dashboard → Action scene.turn_on → Target selection scene.movie_mode
  • Automation: Action Segment scene.turn_on
  • Voice assistant: Say "movie mode" after exposing the scene

Advanced: add a transition

The scene itself is an "instant switch", but you can add transition: 5 Let the light entity fade over for 5 seconds:

action: scene.turn_on
target:
  entity_id: scene.movie_mode
data:
  transition: 5

Scene versus script

Scene: Only "final state of all entities" can be set, all at once, no sorting, no delay, no conditions.
Script: You can have sequences, delays, conditions, and loops, but each action must be written step by step (Action, the old version is called Service).
Common combinations: Call scene in the script - "Movie Mode Script" = call "Movie Light Scene" + wait 2 seconds + close the curtains + turn on the TV.

Helpers: give automations memory

A helper is a virtual entity built into HA - it has no physical hardware, but behaves like an entity, has state, can be displayed by the dashboard, and can be used as a trigger/condition.

Why is it needed? An automation does not retain shared state by itself: each trigger is independent. If you want to share state across automations (e.g. "Is guest mode on?"), you need helpers as shared variables.

Path: Settings → Devices & Services → Helpers Tab → "+ Create helpers".

Helper type quick check

1. input_boolean — on/off

A common choice. Common example Scene: "Guest Mode", "Vacation Mode", "Sleep Mode".

  • Create: Type "Toggle" → Name "Guest Mode" → Entity ID: input_boolean.guest_mode
  • As a condition: Automate "Turn on the lights at sunset" plus condition input_boolean.vacation_mode == off(Do not turn on the lights when on vacation)
  • As a trigger: when input_boolean.guest_mode changes to on, notify the owner that a visitor has arrived.
  • Dashboard: place it on an Entities or Tile card so household members can change it.

2. input_number — Adjustable numbers (slider or box)

Move adjustable values out of automation YAML so household members can change them from the dashboard.

  • Example:input_number.motion_light_brightness = The brightness of the light when the action is triggered. If you want it to be darker at night, slide the slider to change it.
  • Quoted in automation:brightness_pct: "{{ states('input_number.motion_light_brightness') | int }}"

3. input_select — Drop-down menu (select one from multiple)

Classic usage: household state machine. build input_select.home_mode Options = [At Home, Away from Home, Sleeping, Visitor, Vacation], all automation is based on this condition.

Benefit: One centrally managed mode avoids conflicting combinations of 5 separate booleans.

4. input_text — Text

Common scenes: notes, tags, dynamic string references. Example:input_text.tv_url Stores a media URL and use it as play_media for the media button.

5. input_datetime — date / time / both

Let household members set values such as a wake-up time or water-heater start time. Select this entity in an automation’s time trigger so the automation runs at the chosen time.

triggers:
  - trigger: time
    at: input_datetime.wake_up_time

6. timer — countdown timer

More flexible than "delay": it can be queried for the remaining time, can be canceled, and triggers events when it ends.

  • Create: Type "Timer", you can set the default duration duration: "00:05:00"
  • Start:timer.start(accepts a duration overwrite)
  • Cancel:timer.cancel
  • End trigger: for automation event_type: timer.finished event trigger
  • Common example: The motion sensor lights up for 5 minutes - "action → turn on the light + start the timer; when the timer reaches → turn off the light", and then move again in the middle timer.start(Will restart).

7. counter — integer counter

Can be added, subtracted, and reset. Track "how many times were the doors opened today" and "how many times were watered this week" and use the dashboard to see trends.

8. input_button — momentary button

Similar to input_boolean, but it does not retain an on state when pressed, and only a "pressed" event will be sent. Dashboard buttons suited to "execute once", such as "Refresh Data" and "Send Test Notifications".

9. schedule — Weekly schedule

Draw a grid-style weekly schedule. Example: "Working Hours" = Monday to Friday 09:00-18:00. The entity state automatically changes based on the current time on / off.

A schedule is easier to maintain than several handwritten time conditions, and household members can adjust its periods from the dashboard.

10. Template / Threshold / Derivative / Statistics, etc.

You can also create advanced helpers such as "template sensor", "threshold binary_sensor", "derivative sensor", and "statistics sensor" are also on this page, built with UI. For example:

  • Threshold: put sensor.pm25(number) converted to binary_sensor.air_bad(over 35 = on), to make automation conditions easier to read
  • Statistics: Calculate "average temperature in the past 24 hours" and "daily meter total"
  • Derivative: Calculate "power consumption change rate" and "temperature rise rate"
Use a helper before writing a template: Beginners often rush to write the Jinja template sensor as soon as they encounter "conversion". A built-in helper handles many common conversions and remains understandable to other household members. Use a template only when no helper fits.

Groups: combine multiple entities

A group combines multiple entities of the same domain into a new entity. The state of this new entity is the "aggregation of all members".

Common uses

  • Light group: light.livingroom_all = main light + atmosphere light + floor lamp, turn on all with one click
  • Switch group: switch.holiday_lights = 5 Christmas light sockets
  • sensor group: binary_sensor.any_window_open = 5 window magnets, on when any member is on (useful for "checking when leaving home")
  • Person group: group.family = 4 persons, "Is anyone at home" = home

How to build

Settings → Devices & Services → Helpers → "+ Create helper" → Select "Group" → Select the type (Light / Switch / Cover / Binary sensor / Media player / Fan / Lock / Sensor) → Select members.

Aggregation behavior

Type Default state logic Adjustable
Light / Switchany on → group onCan be changed to "on only when all are on"
Binary sensorDefault all (on only when all are on)Can be changed to any (any on)
SensorNumeric aggregation (min/max/mean/median/sum/last/range)Select when creating

Control all members through the group

light.turn_on target: light.livingroom_all expands to turn_on for all members. This is cleaner than writing "target and select 5 entities" yourself, and adding new lights only requires entering the member list.

Group vs Area vs Label: All three can "control multiple at once". Difference:
  • Group: A clear list of members, aggregated into a new entity, which can have logical states
  • Area: Physical location; best for commands such as “turn off everything in the living room.”
  • Label: Cross-region and cross-domain tags, suited to concept groups such as "all main lights" and "outdoor devices"
In practice: Group is used for long-term fixed "a group of lights acts as a group"; Area is used for location-based control; and Label is used for cross-area categories.

Combined example: bathroom night-light system

Put the scene + helper + group together to create a complete system of "bathroom motion-triggered night light". Requirements:

  • Someone enters the bathroom late at night → Only turn on the dim night-light (do not turn on the main light to cause glare)
  • No motion for more than 5 minutes → fade out and turn off the lights
  • No action during the day (judge by sunlight or time of day)
  • The brightness can be adjusted by family members themselves

Build it

  1. Create a group light.bathroom_all = main light + mirror headlight + night light
  2. Create a scene scene.bathroom_night_soft = only night light on, brightness input_number.bathroom_night_brightness
  3. Create helpers:
    • input_number.bathroom_night_brightness(1-100, default 20)
    • timer.bathroom_light(default 5 minutes)
    • schedule.night_time (22:00-06:00)
  4. Write automation ​​: 
    alias: Bathroom night-light motion
triggers:
  - trigger: state
    entity_id: binary_sensor.bathroom_motion
    to: "on"
conditions:
  - condition: state
    entity_id: schedule.night_time
    state: "on"
actions:
  - action: scene.turn_on
    target: { entity_id: scene.bathroom_night_soft }
  - action: timer.start
    target: { entity_id: timer.bathroom_light }
  5. Write another one "timer completed → turn off the light": 
    alias: Turn off bathroom motion light
triggers:
  - trigger: event
    event_type: timer.finished
    event_data: { entity_id: timer.bathroom_light }
actions:
  - action: light.turn_off
    target: { entity_id: light.bathroom_all }
    data: { transition: 3 }
  6. Put a "Brightness" slider on the dashboard (Entity card of input_number.bathroom_night_brightness), the family adjusts it themselves.
Why this design works: It uses 4 helpers, 1 group, 1 scene, and 2 automations. The logic remains visible to other household members. To extend the light period to 10 minutes, change the timer default without editing either automation. This is the value of using helpers instead of hidden template constants.

FAQ

Can the scene change dynamically (for example, changing the brightness according to the time of day)?
The scene itself is a fixed value. Use "script + input_number" to achieve dynamic requirements, or create several different scenes (breakfast, lunch, evening) and use an automation select among them.
Will Helper data be backed up?
Yes, the helper is part of the HA config, in the full backup in Chapter 9. They return when you restore that backup.
Will making a member of the Group unavailable affect the group status?
Yes. By default, unavailable members will change the overall status of the group unavailable. You can check "Ignore unavailable members" when creating a group.
Will deleting the helper affect the automation that uses it?
Yes, the reference will become an error (the entity does not exist). Before deleting, check Settings → Tools → States (the old version was "Developer Tools → Status" in the sidebar) to see who is citing it, or edit each automation to replace the reference.
Is the Timer accurate enough? Can I do a 30 second cooking timer?
Home Assistant’s built-in timer uses second-level precision, which is generally sufficient. A restart can pause or reset it depending on its restore setting. For a YAML-defined timer, add restore: true if you need to retain the remaining time across restarts.
